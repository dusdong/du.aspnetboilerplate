# 局部升版的公开验收

## MODIFIED Requirements

### Requirement: 发行身份和发布权限可核对

发行记录必须（SHALL）将主仓 tag 指向的提交、三个生产 gitlink、批准的发布者与目标、冻结批次及该批全部实际上传输入的身份和摘要关联起来。R4 首发按原清单核对 26 份上传件，R5 局部补丁只发行新三包的主包及符号包，另列出十个沿用的 R4 公开包。

#### Scenario: 输入和授权均已就绪

- **WHEN** 发布者取得 R4 首发批次对主仓 tag、GitHub Release 及 nuget.org 包与符号的相应授权，且核对了账号权限、名称和版本
- **THEN** 发行记录列出主仓 tag 目标、11 个框架包及两个映射包的确切版本、生产提交和各自的主包及符号包摘要，允许执行已授权步骤

#### Scenario: 局部发行的输入和授权均已就绪

- **WHEN** R5 批次的 tag、GitHub Release、三个新版本及对应符号的授权、发布身份和冻结实物均已核对
- **THEN** 发行记录将 tag 目标、协调提交、三个生产 gitlink、三个主包及三个符号包的 ID、版本和上传摘要关联到同一批次，并列出十个沿用包的版本及其 R4 公开证据

#### Scenario: 外部写入前发现差异

- **WHEN** 授权缺失、同名 tag 指向其他提交、生产 gitlink 不符，或待上传归档的字节与冻结登记不符
- **THEN** 发布者在受影响的公开操作前停止，并记录需要解决的具体差异

### Requirement: 部分发布后可以安全续作

发布者必须（SHALL）分别登记 tag、每个主包、每个符号包与 GitHub Release 的外部状态。上传主包前，发布者必须（SHALL）确认其冻结 nuspec 各目标组引用的每个直接内部依赖均已按本批版本通过匿名下载、仓库验签与冻结内容核对。R5 主包及符号包发起上传前必须（SHALL）在同一进度目录按冻结批次和归档种类分别持久化上传意向，记载包 ID、版本、归档 SHA-256 和该次操作的收据路径。意向持久化失败时停止该上传。

#### Scenario: 上传结果不确定或索引延迟

- **WHEN** 上传超时、服务已受理但索引仍不可见，或进程在部分上传后中断
- **THEN** 后续执行先回读对应包和符号的服务状态，保留已确认项，并逐项记录待核对或待上传的身份。已受理的包须经独立下载验证后才能登记公开可消费

#### Scenario: 主包受理后在本地记账前中断

- **WHEN** R5 主包上传已受理且在受理结果持久化前中断，以同一进度目录重启时匿名下载仍返回 404
- **THEN** 放行检查从已存的主包意向识别待查证的上传，继续查收据及服务状态，上传调用次数保持不变。确认归属且仓库验签和冻结内容核对通过后，登记结果并接续

#### Scenario: 符号包受理后在本地记账前中断

- **WHEN** R5 符号包上传已受理且在受理结果持久化前中断，以同一进度目录重启时符号服务尚未返回 PDB
- **THEN** 放行检查从已存的符号包意向识别待查证的上传，继续查收据及符号服务状态，上传调用次数保持不变。确认归属且公开 PDB 的调试标识和内容与冻结输入相符后，登记结果并接续

#### Scenario: 已有上传意向需要重新提交

- **WHEN** 该项尚无确认结果，发布者请求重试同一主包或符号包
- **THEN** 仅在已有明确证据表明上次上传未获受理并通过其原有放行检查时允许重试。单凭主包 404、暂无 PDB 或本地受理记录缺失，继续保留意向并查证

#### Scenario: 通过 GitHub 托管 runner 提交 R5 归档

- **WHEN** R5 使用 nuget.org Trusted Publishing 上传某一份冻结归档
- **THEN** 先验证相同 `main` 提交在 `nuget-r5` 环境能完成 OIDC 登录，且登录验证运行跳过上传。通过本地依赖放行、冻结摘要核对并持久化上传意向后，把该件归档绑定到一个已登记的 GitHub 运行。该运行只可在首次尝试中向官方源提交一个 SHA-256 匹配的实物，并分别保留 GitHub 运行和 NuGet 上传结果。触发新运行或重新运行旧作业均不能复用其放行

#### Scenario: 草稿承载待发归档

- **WHEN** 发布者使用目标附注 tag 的 Release 草稿为托管 runner 暂存归档
- **THEN** 草稿在上传阶段仅含三份主包和三份符号包原件。公开 Release 前移除暂存归档，沿用原草稿交付已通过公开验收的发行说明及校验清单

#### Scenario: 局部升版控制主包与符号放行

- **WHEN** 引擎、Collection 和适配器以新版本发行，另外十个维护包沿用公开 R4
- **THEN** 先核验十个沿用包的公开证据。引擎主包公开核验通过后才能上传 Collection 主包，适配器主包还需要新 Collection 和沿用的 `Du.Abp [10.5.1]` 核验通过。每个新符号包须在对应主包公开核验通过后才可上传

#### Scenario: 上游主包已受理但尚未核验通过

- **WHEN** `Du.AutoMapper 14.0.0` 已受理，但尚不能匿名下载或未通过仓库签名及逐文件核对
- **THEN** 暂停上传 `Du.AutoMapper.Collection 11.0.0` 及依赖它的主包，记录阻塞的依赖和版本。独立且已满足自身依赖条件的主包可继续上传
- **AND** 引擎核验通过并登记其公开下载 SHA-256 后即可上传 Collection，即使引擎的符号仍待索引

#### Scenario: 目标版本已存在

- **WHEN** 公开源已有相同 ID 和版本
- **THEN** 发布者核对所有者、该批发布记录及公开内容。已证明属于本次发行的项目可接续，归属或内容有冲突的项目停止发布并保留证据

### Requirement: 公开主包和调试符号可追溯到冻结输入

核验记录必须（SHALL）关联每个主包的上传摘要、公开下载摘要、经过信任验证的 nuget.org 仓库签名及内容核对结果，并提供每个发行目标的符号服务读回结果。

#### Scenario: 公开仓库对主包签名

- **WHEN** 消费者匿名下载该版本，仓库签名改变了归档字节
- **THEN** 核验器验证仓库签名及签名来源，按路径逐项对照冻结包内文件的集合与内容。通过时保留上传和下载两份摘要及签名差异的解释

#### Scenario: 主包内容存在额外差异

- **WHEN** 签名无法验证、公开主包缺少一个文件、出现签名以外的新文件，或已有 DLL、nuspec 等文件的内容发生变化
- **THEN** 即使版本号相同也将该主包记为核验失败，报告包、路径或签名原因，保留两个版本的摘要以便定位

#### Scenario: 调试器请求符号

- **WHEN** 使用公开主包中的 DLL 向 nuget.org 符号服务请求其 Portable PDB
- **THEN** 按包、目标框架及 DLL 记录读取结果，将调试标识与 PDB 内容核对至相应的冻结符号。本批的全部目标均匹配后才登记符号验证通过。R4 首发为 18 个目标，R5 局部补丁为三个新 PDB

### Requirement: 公开源消费结果决定发行完成状态

项目必须（SHALL）在干净的固定模板中从 nuget.org 独立还原公开版本，记录四个 Release 入口的资产与进程结果，以及 SQL Server 和 Angular 代表性业务的实际观测。发行说明必须提供普通消费者可用的版本、命令、链接和实测范围。

#### Scenario: 两代模板从公开源运行

- **WHEN** 分别用空缓存和仅含 nuget.org 的包源配置运行固定模板的 `net9.0` 和 `net10.0` Web.Host 与 Migrator
- **THEN** 两代还原图分别包含 Host 所需的 13 个和 Migrator 所需的 10 个维护包。构建、启动、数据库迁移、两代同库接续、租户登录及授权查询均有实际结果，每个入口按包 ID 和版本将缓存中实际还原的 `.nupkg` SHA-256 与已验签并经内容核对的公开下载 SHA-256 比对。编译引用、Release 输出和进程实际加载的维护 DLL 均匹配所选冻结资产的 SHA-256。按需依赖记录输出及实际加载状态

#### Scenario: 混入本地资产或缺少公开证据

- **WHEN** 还原使用了本地源、旧缓存、维护组件的项目引用，缓存主包与已验签的公开下载摘要不符，维护 DLL 与冻结资产摘要不符，或仍有主包、符号或消费者结果待核实
- **THEN** 该次运行不能登记为本批公开发行验收通过，记录受影响的入口、包或资产及失败原因，列出待补证据

#### Scenario: 普通消费者按发行说明完成新安装

- **WHEN** 消费者匿名取得固定模板，在干净目录使用独立空 NuGet 缓存、仅含 nuget.org 的包源配置、新建的空 SQL Server 测试库和发行说明草案列出的公开材料，逐条执行 `net10.0` 安装命令
- **THEN** Migrator 成功退出且新库可查到模板迁移记录，Web.Host 启动并返回说明约定的 HTTP 成功响应。记录实际执行命令和结果，供发行说明引用
- **AND** 说明中用到的发行 tag 之后新增的脚本可按固定提交匿名取得。若需读取发布者交接目录、历史运行报告、验证机冻结的 Angular 输出或数据库备份，或任一步骤无法按说明完成，须修订说明或入口并重新通过本场景后才能发布 GitHub Release
- **AND** R5 使用公开可定位的固定指南版本与公开模板提交 `2e9536872673a7ff1986a19e798c51684d16afe5`。Core 使用 `Du.Abp.AutoMapper [10.5.2]`，安装涉及的其余直接引用的沿用 Du 包使用 `[10.5.1]`。实际还原图须确认 `Du.AutoMapper 14.0.1`、`Du.AutoMapper.Collection 11.0.1` 和 `Du.Abp.AutoMapper 10.5.2`，Web.Host 的 `/swagger/v1/swagger.json` 须返回 HTTP 200

#### Scenario: 发布可供用户采用的发行说明

- **WHEN** 本批所需的公开实物核验和真实公开消费均已通过。R4 首发要求 13 个主包、13 个符号包、18 个符号目标、两代公开源业务回归及普通消费者按发行说明的新库安装均通过验证。R5 局部补丁要求三个新主包、三个新符号包、三个公开 PDB 和十个沿用包通过核验，并完成本批实际公开源 `install`、`upgrade` 及从公开固定指南版本执行的独立消费者新装
- **THEN** GitHub Release 关联已核实的主仓 tag、三个生产提交、包页面、可公开的摘要、安装命令和实测支持矩阵，并标明本次公开源实测与此前本地回退证据的来源。新安装示例使用 `net10.0`，`net9.0` 标为存量应用迁移兼容性实测，并注明两代实际运行时及微软结束 .NET 9 支持的日期 `2026-11-10`。R4 首发记录的两代实测运行时分别为 `10.0.15` 和 `9.0.10`
- **AND** R5 的说明标明三包精确版本、十个沿用包及各自的证据来源，链接独立新装已经实跑的公开固定指南版本。R4 公开历史及此前 R5 本地候选或回退记录须标明原批次和验证范围，与 R5 本次实际公开下载与运行证据分别列明。发布后核对归属 tag 与公开校验附件字节
