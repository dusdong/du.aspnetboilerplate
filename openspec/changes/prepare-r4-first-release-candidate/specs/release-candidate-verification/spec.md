# 首次发行候选验收

## Purpose

让维护者可以从明确的源码提交制备一套带稳定版本号的安装包和符号包，从干净环境验证实际消费者使用的版本与运行文件，并把这些具体文件及其支持范围交给发布者。

## ADDED Requirements

### Requirement: 首发组合具有明确的版本和生产来源

维护者 SHALL 为固定模板实际使用的 11 个框架包和两个映射包登记唯一的待发版本组合，记录协调仓输入、三个生产仓库的精确提交，以及每包每个 TFM 的内部依赖范围。

#### Scenario: 从已交付的预发布组合建立待发清单

- **WHEN** 维护者以 R3 冻结归档作为比较输入
- **THEN** 清单逐包关联旧 ID、版本和摘要与待发 ID、稳定版本、目标资产及生产提交。五个核心包保留双目标，六个框架模块保留 `net9.0`，两个映射包保留 `net8.0`
- **AND** 从实际 nuspec 读取的每条内部边均匹配约定版本范围。第三方依赖、框架引用及其归属与比较输入的差异逐项可解释

#### Scenario: 范围、来源或候选身份不一致

- **WHEN** 实际包引用旧预发布批次、缺少内部依赖、范围与登记不符，或生产树包含未归入选定提交的输入
- **THEN** 该组合不能进入待发状态，报告指出包、目标组、期望值与实际值。同一候选的既有文件保持可追溯

### Requirement: 主包和符号包可追溯且保留兼容契约

每份主包 SHALL 从已登记的子仓提交构建，并与对应符号包、源代码、适用许可和实际 DLL 身份一起验证。

冻结前，维护者 SHALL 从实际主包核对包身份、项目主页和随包安装指引，确认消费者可以据此找到维护项目并安装对应的维护包。

#### Scenario: 验证归档中的实际内容

- **WHEN** 从干净的生产输入生成本轮归档
- **THEN** 得到 13 对 ID 和版本匹配的 nupkg、snupkg，每个归档有长度和 SHA-256。主包 nuspec 的仓库地址及提交与实际生产者一致，各 TFM 的 Release DLL 与对应 Portable PDB 匹配，符号来源可定位到该提交的源码
- **AND** 用已验收的同目标 DLL 核对程序集名、公钥标识（如适用）、程序集版本、公共类型和 API。核对项目 RootNamespace、包内许可和声明。文件版本及构建标识的变化须记录

#### Scenario: 从主包核对维护版主页和安装说明

- **WHEN** 维护者在冻结前检查 13 份 nupkg
- **THEN** 各包 nuspec 的 `id` 和 `projectUrl` 分别匹配清单中的维护包 ID 与主页。随包 README 中用于安装该包的命令及链接均指向该维护包，维护联系入口指向维护项目，上游署名、版权和许可得到保留
- **AND** 若引擎 README 仍引导执行 `dotnet add package AutoMapper`，或包主页仍指向上游项目，则停止冻结，报告包 ID、出错字段或包内文件及期望值与实际值

#### Scenario: 同名文件与来源或符号不匹配

- **WHEN** 某包来自错误提交、缺少适用的许可或符号、PDB 与 DLL 不配对，或出现未说明的公开 API 与类型身份变动
- **THEN** 验收失败并可定位到具体包、TFM 或文件。重新生产的归档使用其自身摘要重新验收

### Requirement: 消费者只从本轮待发组合安装维护包

固定模板 SHALL 使用独立空缓存，从本轮包源为两个目标运行时分别还原和构建 Release Web.Host 与 Migrator，并能将本轮维护依赖从包源追溯到实际处理业务的进程。

#### Scenario: 两个入口从最终归档还原

- **WHEN** 在固定模板提交上应用本轮包映射，以 `net9.0` 和 `net10.0` 分别还原
- **THEN** 在两种目标下，Host 解析 13 个维护包，Migrator 按其项目图解析 10 个。每个包的来源和摘要匹配本轮清单，各 TFM 的编译引用、运行资产及适用 RID 能与归档核对
- **AND** 对实际运行的入口，通过进程 PID、入口 DLL、共享运行时、EF Core、SQL Server Provider、框架及映射程序集的来源确认运行组合。对仅进入输出的依赖记录加载状态

#### Scenario: 空缓存缺包或混装

- **WHEN** 受控源缺少本轮归档、同 ID 和版本文件摘要不符，或框架项目引用、原版、其他发行线或旧候选进入维护包闭包
- **THEN** 拒绝该消费结果并记录来源、入口和包，构建可用性与完整业务验收分别报告

### Requirement: 待发结论对应同一批归档的本地业务实测

维护者 SHALL 使用同一批已核验归档复跑代表性模板的维护版安装、同库升级和原版回退，并将业务结果与这些归档绑定。

维护者 SHALL 对冻结的 `Du.AutoMapper` 主包按[映射包稳定规范](../../../../specs/automapper-package-consumption/spec.md#scenario-判断安全修复能否纳入候选)复验三项已登记安全修复，全部通过后方可交接。

#### Scenario: 从本轮引擎归档逐项复验安全修复

- **WHEN** 维护者从本轮冻结源安装引擎，针对 GHSA-rvv3-g6hj-g44x、GHSA-6vhm-j9h7-f9gh、GHSA-gpwp-5797-mjff 执行既有回归
- **THEN** 每项证据关联本轮主包和隔离子进程实际加载的 `AutoMapper.dll` 的 SHA-256。主包摘要匹配冻结清单，加载文件与主包内 DLL 同摘要，报告记录各项预期与实际结果
- **AND** CLR 低栈分支沿用稳定规范的三项组合证据，明确记录受控异常由测试注入、实际 CLR 低栈触发未观测。缺少任一必需证据、断言失败或摘要不符时，该批验收失败并指出对应公告

#### Scenario: 升级和回退通过

- **WHEN** 从 R3 已验证的登录前备份开始，用本轮待发包先运行 .NET 9 维护版，再用 .NET 10 维护版接手同一候选库
- **THEN** 两代均用冻结 Angular 客户端完成 `Default` 登录、`Pages.Users` 授权及关键词请求，返回并显示唯一预期用户。核对迁移历史、数据库目标和登录行的保留及增量，并产生本轮升级前、后的恢复点
- **AND** 固定原版应用从本轮两个恢复点分别复跑登录和查询，正确保留各恢复点的历史行，对照库无当轮增量。结果通过请求和数据库观测关联到对应的应用和恢复点

#### Scenario: 交接本地通过的发行候选

- **WHEN** 实际归档、必要组件回归及本轮消费者结果均通过
- **THEN** 清单、校验值、发布说明草案和支持矩阵使用同一组生产提交及包摘要，列出每个已验证组合、已知限制和待验组合。交接状态为本地待发，发布记录与公开源消费者结果由后续发行补齐

#### Scenario: 仅有历史结果或归档已变化

- **WHEN** 仅有 R0 CI 或 R3 业务结果，或完成验收后发生重新打包、改版本或发布者签名导致文件摘要改变
- **THEN** 报告标明历史证据或受影响的检查，变更后的归档完成来源、完整性及相应消费复验后方可列为待发文件
