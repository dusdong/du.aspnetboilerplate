# Design

## Context

动机见[提案](proposal.md)。固定模板的 `UserMapProfile` 在更新已有实体时忽略 `Roles` 和 `CreationTime`。`UserAppService.UpdateAsync` 按 ID 加载用户，映射后更新普通字段，只在 `RoleNames != null` 时调用 `SetRolesAsync`，最后调用 `GetAsync` 返回 DTO。框架的 `SetRolesAsync` 先移除不在请求中的角色，再添加缺少的角色。模板 `MapToEntityDto` 从 `user.Roles` 取得直接分配的角色 ID，再将对应角色的 `NormalizedName` 写入响应。上述代码给出阶段预期，提交结果由正式运行确认。[模板更新与返回映射](../../../../module-zero-core-template/aspnet-core/src/AbpCompanyName.AbpProjectName.Application/Users/UserAppService.cs) · [输入映射](../../../../module-zero-core-template/aspnet-core/src/AbpCompanyName.AbpProjectName.Application/Users/Dto/UserMapProfile.cs) · [角色管理实现](../../../../aspnetboilerplate/src/Abp.ZeroCore/Authorization/Users/AbpUserManager.cs)

## Goals / Non-Goals

目标是将每个更新请求、独立 API 读回和已提交的 SQL 行绑定到该版的实际包、进程、数据库和种子。验收覆盖默认租户的一名普通用户及其直接角色关联（`dbo.AbpUserRoles`）。组织单元继承角色、用户最终拥有的权限、其他客户端、平台、Provider 和生产改动由各自的变更覆盖。既有回退和 SQLite 映射仍使用历史证据。

## Decisions

1. **复用公开消费的准备与核验步骤。** 以模板 `2e9536872673a7ff1986a19e798c51684d16afe5` 及 R4 `v10.5.1`、R5 `v10.5.2` 的发布校验附件为输入。在两份隔离的模板副本中复用指南的模板准备、升级引用、公开附件、空缓存还原及产物核验逻辑，保持源文件和项目调整等价。使用 macOS ARM64、SDK `10.0.404`、`net10.0`、.NET 与 ASP.NET Core `10.0.15`、EF Core SQL Server `10.0.15` 和 SQL Server Developer `16.0.4236.2`。旧公开组合为适配器 `10.5.1`、引擎 `14.0.0`、Collection `11.0.0`，新版依次为 `10.5.2 / 14.0.1 / 11.0.1`，其余十个维护包沿用 R4。两边只直接引用对应版的映射适配器。用现有图核验逻辑对照 Web.Host、Migrator 各自的完整还原图、签后实物和输出，口径沿用 13 个、10 个维护包及已登记的四条精确依赖边。业务结束后从本次 Host 核验实际加载的适配器与唯一映射引擎及其文件摘要，核对 SQL Server Provider 和共享框架。三份映射 DLL 均对账所选包内资产和输出，Collection 按实际加载状态报告。既有整轮切换入口的业务和数据库阶段用于其原有验收。[公开指南的演练脚本](../../../../docs/maintenance/r5-consumer-package-rollback.md#演练脚本) · [现有包图核验](../../../../eng/r5_public_switch_assets.py) · [现有运行资产观测](../../../../eng/r5_template_consumer.py)
2. **隔离真实数据库与进程。** 每侧使用新建的专用空库、该侧实际构建的 Migrator 和独立 Host，固定环回 SQL 实例及各侧的 Host 监听端口。启动前核对连接目标并登记各侧实例、库名、数据库 ID 和 GUID，确认两侧使用不同数据库。记录两库迁移清单和默认租户的种子事实，该租户使用各侧默认库。用目标租户内的种子管理员做唯一操作人，复用实际认证和会话读回。通过 `POST /api/services/app/Role/Create` 建立两枚普通测试角色，A 的 `name` 和必填 `displayName` 分别是 `du-role-a`、`Role Check A`，B 对应 `du-role-b`、`Role Check B`，均提交 `grantedPermissions: []`。用公开 API 回执、`dbo.AbpRoles` 与 `dbo.AbpPermissions` 确认名称、本库角色 ID、租户、非静态、非默认及没有授予的权限记录。再通过 `POST /api/services/app/User/Create` 创建只含 A 的普通用户。必填的 `password` 复用消费者指南的随机临时密码生成及脱敏方式，各侧在进程内生成并用于创建请求，留存证据均脱敏。后续始终用该侧创建回执中的 ID。[角色种子](../../../../docs/maintenance/r5-template-user-role-update-plan.md#固定输入与种子) · [固定用户字段](../../../../docs/maintenance/r5-template-user-role-update-plan.md#三步真实更新)
3. **用原始 HTTP 明确表达三个输入。** 更新走 `PUT /api/services/app/User/Update`，另发 `GET /api/services/app/User/Get?Id=<id>` 核对已提交状态。复用指南的 `read_api` 时，更新调用须显式指定 `PUT` 并记录实发方法，既有调用继续按有无请求体默认使用 POST 或 GET。生成的 Angular `UserDto.toJSON` 仅在 `Array.isArray(this.roleNames)` 时写出该键，因此直接发送 JSON 以保证首步有字面 `"roleNames": null`，后两步为 `["<B 的 Name>"]` 和 `[]`。每步记录请求 JSON、HTTP 状态和 ABP 信封的 `result`，要求回执和 GET 的 `roleNames` 均为实际数组。角色请求使用经 Role/Create 确认的原始 `Name`，角色响应以同一角色行的 `NormalizedName` 作精确集合对照。排序和自增 ID 随各库运行，集合缺失、重复或额外成员均计失败。[角色创建](../../../../module-zero-core-template/aspnet-core/src/AbpCompanyName.AbpProjectName.Application/Roles/RoleAppService.cs) · [DTO](../../../../module-zero-core-template/aspnet-core/src/AbpCompanyName.AbpProjectName.Application/Users/Dto/UserDto.cs) · [生成代理](../../../../module-zero-core-template/angular/src/shared/service-proxies/service-proxies.ts)
4. **逐请求核对 Host 访问的数据库。** 初态独立 GET、每步 PUT 和随后独立 GET 各有唯一请求标识。Host 将请求标识、实际 PID、方法、路由及目标用户 ID 关联到该请求处理该用户的 EF 命令，从命令实际使用的连接读取 SQL Server 实例与库名，再按实测实例与库名核对当前数据库 ID、GUID 与该侧预检记录是否一致。认证、会话查询或验收端独立 SELECT 均不能证明业务命令访问了该库。现有观测器按关键词和分页参数匹配 `User/GetAll`，应保留该路径的行为，另对 `User/Update` 和按 ID 的 `User/Get` 验证关联。若任一请求缺少业务连接证据，或实测库与该侧预检记录不符，则停止该侧后续写入。[现有 Host 观测器](../../../../eng/r3-template-observer/StartupHook.cs)
5. **在独立 SQL 连接上查实提交。** 每步以参数化只读 SELECT 从 `dbo.AbpUsers` 按本库租户及用户 ID 取得唯一未删除的行，核对 `UserName`、`Name`、`Surname`、`EmailAddress`、`IsActive` 和 `CreationTime`。另从 `dbo.AbpUserRoles` 按目标用户 ID 读取全部关联，左连接 `dbo.AbpRoles`，核对关系两端的租户与角色 ID、`Name`、`NormalizedName` 和删除状态，使孤立、错租户、重复或多余关联能显示在证据中。清空阶段要求零关系行。角色行仍可按本库身份查询。API 的 `UserDto` 没有 `TenantId`，租户用认证会话和 SQL 用户行对账。每侧先用初态 GET 和 SQL 绑定原创建时间，再核对每步均等于该侧原值且有别于请求值。SQL Server 的 `datetime2` 用 ISO 126 文本保留小数秒，按实际 JSON 序列化语义以同一精度比较。模板默认的无时区时间按本地表盘值比较，不给无偏移存储值强加 UTC。保留原始字符串，跨库只比较创建时间保留这一不变量。
6. **将证据记录和报告判定绑定到步骤。** 各步读回结束后才执行依赖该结果的下一步。有请求回执但独立 GET 或断言失败时，仍留存可安全取得的 SQL 读回及原始响应，标出后续未执行。若 PUT 已发出但超时、断连或响应不可解析，该步判失败，停止该侧后续写入，包括重发该 PUT。保存脱敏请求、错误和已收到的响应内容。能核实目标库身份时，以创建回执里的用户 ID 另发独立 GET 并执行只读 SQL，分别记录观测值或无法取得的原因。诊断读回即使符合预期也不能补足 PUT 回执。依赖该步的后续步骤标记未执行。另一侧继续独立验证。总报告按[增量规范](specs/automapper-package-consumption/spec.md)以各侧的预期先判定，再汇总输入不可比、单侧失败、两侧失败或通过。回归使用定向测试或保存证据回放验证共同错误、单侧错误及失配输入的分类，标明其来源。以一侧首步的有效记录构造两个独立反例。一例只换入另一侧的业务连接记录，保留正确的业务数据。另一例在验收入口接收回执处屏蔽成功 PUT 的响应。分别验证该侧后续 PUT 次数为零、另一侧继续且总退出码非零。丢回执反例还要覆盖 GET 和 SQL 都符合预期而该步仍失败。正式成功结论需两侧真实 Host 和 SQL Server 运行的证据。

## Risks / Trade-offs

- 更新回执来自同一更新方法内部的 `GetAsync` → 额外独立 GET 与 SQL 查询共同证明提交。
- 测试基线不一致或连接串被本机配置覆盖 → 先核对还原图、有效连接、实际库身份、迁移和等价业务初态，隔离本机配置和输出。输入不合格的一侧停止后续写入。
- 同一角色名在不同表示中大小写不同，SQL 驱动也可能截短时间 → 使用角色创建后的 `Name`／`NormalizedName` 对照和指定精度的 SQL 文本，保留原始观测。
- 过程中断可能已产生部分写入 → 记录实际读回，复跑使用新的专用空库和证据目录。测试账号密码、SQL 凭据、授权头和 token 仅在进程内使用，报告保留可核对的脱敏字段。
