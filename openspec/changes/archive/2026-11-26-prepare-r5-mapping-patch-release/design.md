# 映射补丁发行准备设计

## Context

主仓 `99f44b7` 对应的三棵源码树与冻结批次 `8d0d4dc762a3582327d8829e5952fadbd55b7448d7c2de85c32e6a76d6a3cf40` 一致。引擎包内 README 指示配置本地包源，现有 R4 公开核验入口固定校验首发清单的 SHA-256。[源码与归档身份](../2026-11-26-fix-r5-automapper-collection-context/three-package-validation.md#批次交接) · [R4 公开核验入口](../../../../eng/r4_public_release.py)

## Goals / Non-Goals

交付可复查的六份待发归档、三个 PDB 目标、十个沿用的公开包、安装及发布说明草案和本地演练结果。运行范围沿用 R5 已测组合，待发件与消费者证据按批次关联。交付状态为本地待发。

## Decisions

1. **从已验实物出发。** 拟用版本依次为 `Du.AutoMapper 14.0.1`、`Du.AutoMapper.Collection 11.0.1`、`Du.Abp.AutoMapper 10.5.2`。先核定拟用主仓 tag 名，再读回该 tag 和 NuGet 三个版本的状态，记录查询时间。目标占用时按归属和实物证据决定接续或重选，重新核定受影响的精确边与验收范围。后两仓的包内编译提交可由已归档的基点、生产补丁和交付提交树对账。
2. **从干净的新引擎提交制备。** 将保留 MIT、署名和维护入口的 README 修订纳入新引擎提交，从该干净提交执行 `pack-r3-engine.sh --r5`，将主包和符号包写入新目录。登记提交、Git 树和打包使用的 `RepositoryCommit`，核对 `source-commit.txt` 及实际 nuspec 的 `repository/@commit` 与打包提交一致。逐成员对照原件，记录压缩封装、README、DLL、PDB、Source Link、nuspec 及签名的实际差异。其余归档符合拟发版本、依赖和符号时可复用原件。验收端独立传入新批次预期摘要。[引擎打包入口](../../../../AutoMapper/src/AutoMapper/ApiCompat/pack-r3-engine.sh) · [本地批次读取](../../../../eng/r5_candidate_batch.py)
3. **按直接依赖回读和续作。** R4 首发沿用固定清单、26 份归档和 18 个符号目标。R5 上传队列仅含三个升版包，共六份归档和三个 PDB 目标，另登记十个沿用包的公开验签证据。引擎回读通过后 Collection 具备依赖条件。即使引擎和 Collection 都已通过，`Du.Abp [10.5.1]` 的 R4 下载验签证据缺失或摘要不符仍会暂停适配器。补齐并核对该证据后，从同一批次进度继续，保留已核实的记录。用 R4 已签名实物走真实验签路径，用隔离样本演练证据缺失、摘要不符、额外文件、版本占用、符号索引延迟和部分受理后重跑。[公开发行规范](../../../specs/public-package-release/spec.md#requirement-部分发布后可以安全续作) · [R4 回读入口](../../../../eng/r4_public_release.py)
4. **按字节差异选择消费者复验。** 用实际待发包空缓存验收独立 ABP 消费，核对四条边、实际加载 DLL 和共享集合业务结果；按既有映射规范复核引擎专项。若只有包装或说明变化，固定模板以两代四入口核对包图、编译与输出资产，业务结果可引用同一运行资产和配置的已验报告。DLL、依赖或运行组合发生变化时，在隔离库重跑受影响的新装、同库接续及包回退场景。[候选验收规范](../../../specs/release-candidate-verification/spec.md) · [模板结果与复跑](../../../../docs/maintenance/r5-automapper-template.md)
5. **演练交付用的公开消费命令。** 保留 R5 候选混合源模式和 R4 首发公开路径。R5 纯 nuget.org 入口按独立的预期摘要核对发行清单、冻结批次和已验签下载登记，逐入口比对缓存包下载摘要及编译、输出和实际加载的 DLL。交接前用最终交付的同一命令和相同校验条件，在隔离目录用 R4 已签名实物及匹配输入演练通过，再分别验证混入本地源与换入错误批次会被拒绝，记录命令、输入、退出码及失败原因。[R5 模板入口](../../../../eng/r5_template_consumer.py) · [R4 模板资产核对](../../../../eng/r4_template_assets.py)

## Risks / Trade-offs

- NuGet 仓库签名会改变下载归档的摘要。真实回读时分别登记上传与下载摘要，验证仓库签名，再逐文件比对冻结内容。发布前用 R4 实物验证该差异的处理。
- 切回 R4 的历史用例证明首阶段写入的业务用户和后续登录行可读。发行说明按此描述回退边界；候选阶段新增其他业务实体的回读、其他平台和数据库继续按实际部署需求验证。

## Migration Plan

交接拟用 tag 名、目标主仓提交及 `git ls-tree` 读出的三个生产 gitlink。若交接时主仓仍指向原引擎 `d264ff75831f12e935df8d4703bb05df99eaa000`，或实际 gitlink 与新制包提交另有差异，则登记实际指针与已制包引擎提交、源码树之间的准确差异，标明 tag 目标待定。打 tag 前须确认新引擎提交可从 `.gitmodules` 登记的子仓取得，由主仓提交固定该 gitlink，并回读最终目标提交的三个 gitlink。

维护者据三个包的精确版本、六份归档、安装说明草案和分步命令决定发行或暂缓。获相应授权后执行 tag、主包和符号上传。实际公开后匿名下载并验签三个新主包，核对签名前后摘要、归档内容和三个服务端 PDB。用已演练的命令从空缓存仅经 nuget.org 还原三新十旧组合，对 `net9.0` 和 `net10.0` 的 Web.Host、Migrator 四入口验证资产和进程，在隔离 SQL Server 库验证新装及两代同库接续业务。公开证据齐备后据实发布 GitHub Release。暂缓时保留批次和待核验状态。
