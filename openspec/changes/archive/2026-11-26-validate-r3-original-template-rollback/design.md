# 原版应用回退设计

## Context

升级轮的 26 个阶段在本机通过。旧版与新版 Migrator 都连接过同一候选库。升级前后比较的 30 条迁移及 36 张表的列、键、索引和外键一致。原专用 SQL Server 已停用，正式报告和两个恢复点仍在。这些输入足以在隔离库重建原版应用需要接手的两个状态。[升级轮正式结果](../../../../docs/maintenance/r3-template-net10-upgrade.md#2026-11-25-正式运行验收)

## Goals / Non-Goals

目标是在 macOS ARM64 原版应用、SQL Server Developer `16.0.4236.2` 和原有 Angular 客户端上验证两种回退步骤。升级后备份用于重建试验起点，在此状态切回应用时保留数据。升级前备份用于实测退回早一恢复点的写入边界。现场流量切换、生产恢复时长、其他业务数据的无损保证和 R4 发行均另行评估。

## Decisions

### 使用原版返修轮的同一套发行物

原版输入来自固定模板 `2e9536872673a7ff1986a19e798c51684d16afe5`，取最终返修轮 `r3-template-runtime-89igcw5r`，其 `report.json` SHA-256 为 `d60dfea17e2d3ffe00d6b1914f429cca7cd60d2a114f913561d62dde0044985c`。核对该报告登记的入口和整份 Release 输出清单，在独立工作目录运行校验过的副本。两项实际共享框架均为 `9.0.10`。11 个上游 ABP 包为 `10.2.0`，上游 AutoMapper / Collection 为 `14.0.0` / `11.0.0`，EF Core 与 Provider 为 `9.0.5`，Unix SqlClient 为 `5.1.6`。沿用 1,193 个文件的 Angular production 产物和 `main-PZGEMKYC.js`，按需仅在前端副本变更两个环回端点。若缺少冻结实物，报告缺项，并按原版手册恢复可核验的输入。[原版复跑手册](../../../../docs/maintenance/r3-template-runtime-baseline.md) · [原版与维护版实际版本](../../../../docs/maintenance/r3-template-net9-packages.md#正式运行结果)

同目标维护包也能在 .NET 9.0.10 运行，且沿用原版 DLL 名称。新入口从原版 `project.assets.json`、`.deps.json`、包内运行资产和 Release 文件清单生成期望值，关联两个进程各自的 PID、启动命令、程序集加载上下文、路径和 SHA-256。现有维护版验证器按 `Du.Abp*` 选文件，并将 .NET 9 Migrator 的 EF Core 期望设为 `9.0.18`。复用其中的进程观测能力，分别传入原版和维护版的期望值，保留历史入口的断言。[原版输出核验](../../../../eng/r3_template_runtime.py) · [维护版运行观测](../../../../eng/r3_template_net10_runtime.py)

### 用两份冻结备份建立可区分的测试库

| 升级后库 | `8df1e277-cde8-4683-a350-9bbf55a48975` | 1、2、3 | 原版直接处理升级后的数据，保留 .NET 10 写入 |

### 两条路径相互对照

两个库的应用操作串行执行。两条路径依次成功时，成功登录计数按“升级后库 / 升级前库”记录为 `3/2 → 4/2 → 4/3`。提交认证前分别读取两库中租户 1、账号 2 的成功登录行，按 ID 排序，将七个字段逐项与恢复点或上一路径已核实的终值比较。业务结束后用同样的查询核对历史行、目标库唯一新增行及对照库。升级轮行 3 的 `creationTime` 为 `2026-11-25T21:55:58.3636350`。在升级前库，认证前读到这笔原始写入即拒绝登录。认证后若唯一新增行重用 ID 3 且创建时间不同，则按本轮写入验收。[七个对照字段](specs/template-application-rollback/spec.md) · [行级查询与增量核对](../../../../eng/r3_template_upgrade_sql.py)

### 核实关键词查询实际读取的库

两个恢复库中用户 3 的数据相同。保留原版 Release 输出，通过 Host 启动观测器只跟踪本轮带指定关键词的 `User/GetAll` 请求。用请求关联标识把浏览器请求、Host PID 和该请求内执行的 EF 用户计数、列表读取命令对应起来。在各命令实际打开的连接及其事务中读回 SQL Server 实例名和 `DB_NAME()`，分别与该路径的目标比较。缺少任一读取的证据、读数来自无关键词的初始列表或任一连接命中对照库，都使该路径失败。[现有启动观测器](../../../../eng/r3-template-observer/StartupHook.cs) · [浏览器关键词请求](../../../../eng/r3_template_browser.py)

### 登录已写入时保留失败现场

现有升级入口在浏览器整轮成功返回后读取两库终值，阶段异常会使外层执行器直接转入清理。回退入口在每条路径内保存业务首错，并在已提交认证的路径结束时回读两库，包括关键词查询失败的情况。回读或清理再次出错时，分别登记错误和缺失的证据。独立诊断在升级后库完成真实登录后使关键词查询失败，检查报告能读回已提交的新行，再从独立恢复点运行升级前路径。诊断结果单独保存，兼容性结论取自正式运行。[现有浏览器阶段](../../../../eng/r3_template_net10_runtime.py) · [现有阶段退出处理](../../../../eng/r3_template_net9_runtime.py)

## Migration Plan

1. 校验原版前后端及升级正式报告和两份介质。恢复两个独立新库，记录备份集、实例、库标识、物理文件和 `ONLINE` 状态。实读两库迁移 ID 与 ProductVersion、业务表目录、租户 1、账号 2、权限依据、用户 3 及历史登录行，对齐升级交接中的相应记录。
2. 将原版 Release `Migrator -q` 连接到升级后库，记录实际迁移命令连接、PID、原版入口和实际 EF/Provider。确认正常退出，数据库迁移历史、所核对的结构及业务数据一致。本轮依据已验结构预期无需逆向迁移。发现差异时保留 SQL 和故障阶段。
3. 在 `Development` 启动原版 Release Host，通过冻结前端和新浏览器会话选择 `Default`、登录并进入受 `Pages.Users` 保护的用户页。核对关键词请求、实际读取库、响应唯一记录和页面唯一用户名单元格，保存进程来源和两库行差。
4. 停止该路径的应用，切到升级前库，使用相同二进制和全新浏览器会话重复步骤 2、3。保存两条路径独立的启动、连接、浏览器、登录与结构对照。第一条路径失败时保留其报告，第二条可单独运行。若先前写入无法核实，从冻结介质新建目标库与对照库，重新核准该轮的起始行。
5. 汇总每条路径的状态，给出可复跑命令、产物和介质定位方式、恢复点与受测写入边界。释放本轮进程和端口，复核两份冻结介质的摘要。R3 路线和迁移手册按实际支持的路径更新。

## Risks / Trade-offs

- 恢复升级前备份会排除该恢复点之后的写入。本例可逐行核实的是测试账号的成功登录记录，手册应明确这一数据范围。
- 依赖可用性或证据缺失会使某条路径无法验证。保留失败或未执行状态，只有可复现的应用与数据不兼容才能作为要求恢复旧备份的依据。
