# 固定模板原版应用回退

## Purpose

让维护者为已升级的经典模板选择有实测依据的回退步骤，确认真正提供服务的原版应用能够登录并读取授权数据，同时可以从升级前后两份恢复介质和实际写入辨认数据保留的边界。

## ADDED Requirements

### Requirement: 回退运行的是已核对的原版应用

回退入口 SHALL 在每条路径使用同一套固定模板原版 Release Migrator、Web.Host 及 Angular production 客户端，并将实际执行迁移和处理业务请求的进程追溯到原版输入。

#### Scenario: 识别提供业务的原版进程

- **WHEN** 维护者从固定提交 `2e953687` 的原版产物运行回退
- **THEN** 两个后端进程的入口文件、实际加载路径和摘要均匹配原版输出。两项共享运行时为 `9.0.10`。各入口的还原图与原版基线一致，Host 的 11 个 ABP DLL 来自原版 `10.2.0` 包，实际 EF Core、Relational 和 SQL Server Provider 均来自 `9.0.5`，SqlClient 来自 `5.1.6`
- **AND** 实际加载的 AutoMapper 引擎唯一且可追溯至原版包。AutoMapper.Collection 的输出和实际加载情况分别记录。浏览器加载冻结客户端的入口脚本

#### Scenario: 同名程序集来自另一发行线

- **WHEN** 误用 .NET 9 维护版或 .NET 10 的入口或 DLL，实际进程与提交的业务请求无法关联，或客户端与冻结清单不符
- **THEN** 该路径失败，报告给出具体进程、文件或缺失的证据，即使版本名相似或页面能够显示

### Requirement: 两个回退起点与升级轮恢复点一致

验证入口 SHALL 按升级正式轮的报告和介质身份，将升级后、升级前状态分别恢复到专用 SQL Server 的两个新库，在原版程序写入之前核实每个库的实际内容。所有登录行比较均限租户 1、账号 2 的成功记录。逐行核对的七个字段为 `id`、`creationTime`、`result`、`tenantId`、`userId`、`tenancyName` 和 `loginName`，与 `sql.checkpoints` 的记录一致。创建时间保留 SQL 记录精度。

#### Scenario: 两份介质分别恢复

- **WHEN** 对 `after_upgrade` 和 `before_upgrade` 分别核对 SHA-256、备份集 ID 并实际恢复
- **THEN** 库名、数据库标识及物理文件可区分。每个库的 30 条迁移 ID 与 ProductVersion、登记的表结构、租户、账号、权限依据及搜索用户与相应恢复点一致
- **AND** 升级后库中租户 1、账号 2 的成功登录记录与正式轮的行 1、2、3 逐行相符，升级前库与行 1、2 逐行相符

#### Scenario: 介质或目标错配

- **WHEN** 备份角色互换、摘要或备份集不符、目标库或文件已占用，或还原后的既有行与指定恢复点不一致
- **THEN** 入口在相应检查失败。拒绝覆盖既有库和文件，保留两份输入介质，不允许在未核准的数据起点上登录

#### Scenario: 升级前库在登录前已有升级轮的原行 3

- **WHEN** 核对升级前库时发现与升级后恢复点原行 3 七个字段均相同的记录
- **THEN** 该路径在提交认证前失败，报告列出预期的行 1、2 及实读的额外记录

### Requirement: 原版应用在两个恢复点完成真实业务

每条路径 SHALL 通过原版 Migrator 的实际 SQL 连接、两库的登录行差异和全新 Angular 会话，证明迁移与登录写入均落在选定库。带关键词的 `User/GetAll` 请求须关联到本轮原版 Host PID，并从该请求执行用户计数与结果列表查询的实际 SQL 连接分别核实实例和库名，两者均须匹配该路径的目标。

#### Scenario: 原版接手升级后的数据

- **WHEN** 原版 Migrator 在升级后库执行常规迁移检查，随后原版 Host 服务首次回退登录
- **THEN** 迁移命令连接的实例和库名与本轮目标一致，PID、入口和实际 EF/Provider 对应原版 Migrator。既有迁移、所核对的表结构和业务记录均保留
- **AND** 在新的浏览器会话用 `Default`（租户 1、账号 2）登录，实际具有 `Pages.Users`。带 `Keyword=r3usercf4314cdfe038c35` 的 `User/GetAll` 请求返回 HTTP 200、总数 1、唯一用户 ID 3，页面唯一数据行的用户名单元格与关键词一致
- **AND** 升级后库三条历史成功登录记录的七个字段均保持原值，仅新增本次一条。升级前库的成功登录记录逐行保持原值

#### Scenario: 原版使用升级前备份恢复的数据

- **WHEN** 原版 Migrator 和 Host 切到由升级前备份独立恢复的库，在新会话重放相同业务
- **THEN** 以相同的进程及 SQL 连接证据确认目标，迁移历史和所核对的表结构一致，原版账号仍有相同权限，实际关键词请求、响应及页面单元格与第一条路径的预期一致
- **AND** 升级前库保留原行 1、2，仅新增本次成功登录，另一库的登录行逐行保持原值。若差集中唯一的新行重用 ID 3，且创建时间与升级轮原行 3 不同，该写入检查通过

#### Scenario: 查询响应正确但读取库无法核实或不符

- **WHEN** 登录写入选定库，浏览器显示预期用户 3，但关键词请求的计数或列表读取命中了对照库、缺少实际连接证据，或观测记录属于另一请求或进程
- **THEN** 该路径失败，报告给出目标实例、库名及实际读数或缺项，并标明对应的请求、Host PID 和查询步骤

#### Scenario: 迁移、登录写入或浏览器业务不符

- **WHEN** Migrator 退出 0 却连错库或缺少连接证据，浏览器只加载了初始列表、权限或响应不符，或实际写入对照库
- **THEN** 该路径失败。迁移身份错误时在启动 Host 前停止，业务阶段失败时保留请求、进程与两库行差异，后续路径只能从独立核准的起点执行

#### Scenario: 升级后库登录已提交，随后关键词查询失败

- **WHEN** 原版在升级后库成功登录，随后该会话的关键词查询失败
- **THEN** 升级后路径记为失败，保留查询首错、阶段和已取得的请求与进程证据。清理前回读两库，与提交认证前的快照按七个字段比较，列出目标库已提交的新行和对照库的实际差异。若回读也失败，另记该错误并将缺少的终值标为未知
- **AND** 从独立核准的升级前库和对照库单独执行第二条路径。汇总报告分别保留两条路径的结果，即使第二条通过，第一条的失败及写入记录仍可查

### Requirement: 回退结论说明适用路径及写入边界

回退报告 SHALL 独立记录两条路径的结果、应用版本、数据库恢复点、历史写入与本次写入，并仅对实际完成的组合给出支持结论。

#### Scenario: 两条路径都完成业务验证

- **WHEN** 原版在升级后库和升级前库都完成对应的迁移检查、登录和查询
- **THEN** 手册可重放两条经过验证的步骤，明确在升级后数据上切回原版可保留 .NET 10 登录行，回到升级前备份会舍弃这条已观测写入。另列受测平台、数据库、浏览器和验证过的业务范围

#### Scenario: 只有一条路径通过或证据不足

- **WHEN** 只有一条路径完成，或实际出现数据不兼容、环境不可用、来源无法核实
- **THEN** 报告分别列出每条路径的通过、失败或未执行状态、出错阶段及可核对的依据。只有查实升级后状态与原版不兼容且升级前路径通过，才可对本组合得出需要恢复备份的结论
