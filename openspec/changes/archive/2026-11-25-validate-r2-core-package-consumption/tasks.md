# R2 实施任务

## 1. 框架子仓候选打包

- [x] 1.1 固定 R2 源码来源和 R1 对照。在隔离框架源码根目录核对 `dotnet --version` 为 `10.0.404`。回读主仓目标 gitlink、框架的确切输入与树，核对 R1 两目标十份 API 清单及产物记录的来源。缺项按设计从相同 R1 树重建并留存命令、输入及摘要。
- [x] 1.2 在已登记五个框架项目接入候选属性。保存 R1 与当前源码普通模式两目标的 MSBuild 求值，核对原 PackageId、PackageVersion、程序集名、根命名空间、目标、项目引用和原打包行为。对一个已登记的 .NET 9 源码调用方做干净 Release 构建并记录结果。
- [x] 1.3 实现并说明候选打包入口，从隔离源码以同一批版本还原和打包。核对显式模式的两目标求值、五组包及符号包、包内源码证明、许可、图标和各目标 DLL。输出供主仓直接验证的候选清单、SHA-256 和实际打包命令，禁止将不同内容写入已分配的候选版本。

## 2. 主仓验证候选产物

- [x] 2.1 在 `eng/verify.py` 接入 R2 验证，读取第 1 组的确切本地包和清单。检查实际 ZIP、nuspec、身份、每目标四条内部边、第三方依赖声明、编译和运行资产，逐份核对包内 DLL 的 `TargetFrameworkAttribute` 与 `lib/<TFM>` 目录，并比较十份 API 清单。分别验证摘要替换、依赖 ID 变异和错目标 DLL 三种负例。错目标用例重算负例清单摘要，要求诊断明确指出包内路径和目标框架差异，并返回非零。检查原 R0 profile 调用及固定输入。
- [x] 2.2 建立两个独立还原的证据提取与判定。核对 `project.assets.json`、实际包来源和摘要、两个入口和三个传递包的版本与资产，诊断混装、包内或输出资产重名和无关引用。用缺失传递包的本地源副本验证隔离还原失败，用受控资产夹具核对错目标和多来源诊断。实际消费者还原在第 3 组接通。

## 3. 主仓独立后端及实跑

- [x] 3.1 在 `validation/minimal-backend/` 接入两个框架入口和各目标 SQLite Provider。每个消费者副本携带固定 SDK 的 `global.json`，在实际执行目录核对 SDK `10.0.404`。启动前核对 ARM64 宿主及两项共享运行时，`net9.0` 对应 `9.0.23`，`net10.0` 对应 `10.0.15`。分别用第 1 组同批实际包在独立空目录和缓存执行还原，用第 2 组检查核对真实资产并完成 `--no-restore` Release 构建。记录配置、命令、来源、项目资产和退出码。
- [x] 3.2 接通宿主、ABP 模块、DI、SQLite 与 ABP 工作单元，运行真实 HTTP 提交和独立作用域读回。按写入请求关联仓储 `DbContext` 的活动事务和负责提交的 ABP 工作单元完成记录，确认提交成功后才返回 HTTP 成功响应。按两个目标断言 HTTP 状态、记录标识和值及唯一行数，记录模块启动、DI、实际运行时、SQLite Provider 和五份已加载框架 DLL 的位置与 SHA-256。
- [x] 3.3 将消费验证整合进 R2 入口并从新目录执行。两目标使用同一批候选、各自空缓存和实际宿主进程，验证报告将候选、还原图、运行资产、实际依赖和业务结果串联。用保留成功读回但缺失写入事务或提交证据的结果验证非零退出和阶段诊断。记录消费项目的本机复跑说明。

## 4. 集成验收与可复核证据

- [x] 4.1 按设计核对同一候选的源码、包、还原与本地运行证据，形成 `docs/maintenance/r2-core-package-consumption.md`，更新文档入口和维护路线。如使用还原锁文件，按目标保存 `packages.lock.json`，记录同批候选的 `--locked-mode` 复跑命令。记录两目标实际通过、失败及未执行项、原始证据定位与摘要，并核对 R0 固定输入、R1 历史及其他子模块范围。
- [x] 4.2 核对实现的仓库边界、候选目录与实际证据，复跑本变更及全量 OpenSpec 严格校验并保留结果。
