# R5 公开发行执行设计

## Context

待发批次的 SHA-256 为 `b914f5669c504a3a85cd7120fb63ff0d14667924d6dd0ff1f92fea9a1a76eaf1`，发行清单为 `2f4ba12a0752739eaafb522d5c9e0a20abd241176646ae31d4748e5102a3fa02`。拟用附注 tag `v10.5.2` 对应主仓 `cebc3e38a511783092963893bf5ad3161d0f0a19`，其生产和模板 gitlink 已逐项从 GitHub 回读。归档后两代公开源构建使用 R4 已签名包，R0 CI 验证该主仓提交上的基线。[已归档手册](../2026-11-26-prepare-r5-mapping-patch-release/release-handoff.md) · [R0 运行](https://github.com/dusdong/du.aspnetboilerplate/actions/runs/45846709281)

## Goals / Non-Goals

交付能由普通消费者匿名取得、验签和安装的局部补丁。复用已交付的六份归档，发布者保留同一进度目录，用独立证据目录记录公开消费。是否清理 52 个重建缓存和是否部署到生产由各自的任务决定。

## Decisions

1. **核定准确目标后才写入。** 重查主仓 tag、三个版本和发布身份，将 tag 目标、三个包及符号的目标源、GitHub Release 与本次明确授权逐项对应。执行时复核原协调提交的四个 gitlink 和批次摘要。若决定暂缓，保留待发清单与现有公开版本。占用冲突先查明归属。发行手册的函数按 POSIX sh 编写，在主仓根目录进入 `/bin/sh` 会话后定义并调用。zsh 的只读变量 `status` 会干扰首次建 tag 和上传失败时的退出码处理。
2. **在实际上传入口先登记意向。** 扩展 `eng/r5_public_release.py` 的放行和记账流程，在同一进度目录内按冻结批次和包种类（主包或符号包）持久化上传意向，记录包 ID、版本、实际归档 SHA-256 和收据路径。使用同一进度锁保护放行检查及意向登记，持久化成功后才调用 `dotnet nuget push`。受理后、本地结果落盘前中断时，重启仍有意向可查。主包 404 或暂无 PDB 时按待查证处理并阻止再次上传。凭收据及远端证据确认受理归属，完成实物匹配后才放行后续步骤。明确证明上次未受理后才登记重试并重新过 gate。首次真实上传前更新实际入口及现行发布者手册，用 `/bin/sh` 分别模拟两种归档在受理后、记账前中断并以同一进度目录重启。发行记录还须注明运行新版上传入口的提交。[原有回读与续作演练](../2026-11-26-prepare-r5-mapping-patch-release/release-rehearsal.md)
3. **把每次托管上传绑定到同一进度目录和唯一的运行。** `publish-r5-mapping.yml` 为 GitHub 托管 runner 的手动工作流，只有发布作业可申请 OIDC 身份，`nuget-r5` 环境限 `main`。先用仅登录模式验证同提交的 `NuGet/login` 交换并读回上传步骤跳过。临时凭据只由同一作业使用。依赖门禁、冻结批次及意向持久化沿用本地入口。六个冻结归档逐项暂存于目标 tag 的同一 Release 草稿。本地上传入口持久化意向后触发单件工作流，将 GitHub 返回的运行 ID 持久化后，再在该件草稿附件 label 写入运行、意向和登录验证 ID。runner 只接受指定仓库、目标 tag、同提交登录验证及当前运行的首次尝试，逐件核对冻结摘要。作业需要 GitHub 的草稿访问权限，通过其 token 下载一个附件，仅将该归档提交到官方 NuGet 源。主包关闭自动符号上传。触发回执与实际上传结果分别登记。若未保存运行 ID，或该运行已终止且上传步骤明确跳过，收据可证明本意向的提交未启动。上传步骤失败或记录不完整时继续核实服务状态。暂存附件在草稿公开前移除。
4. **按依赖控制部分成功。** 先核对十个沿用包。引擎主包公开验签并对账后可发 Collection。适配器还需要 Collection 和 `Du.Abp [10.5.1]` 的证据。符号独立登记，须在对应主包公开核验后上传。沿用 queue、gate、record、verify 的批次和结果核对。公开主包接受登记过的仓库签名差异，其余成员逐一比对。符号按公开 DLL 的调试标识回读并对账。
5. **分别采集发布者和消费者的公开证据。** 用实际签后下载登记及独立摘要运行纯公开源 `install` 和 `upgrade`，留下新库和两代同库四入口证据。面向消费者的 R5 完整指南拟交付至 `docs/maintenance/r5-public-install.md`。以 [R4 安装指南](../../../../docs/maintenance/r4-public-install.md) 的独立安装流程为基础，从匿名可取的固定模板提交运行 `net10.0` 新装。指南应包含前置条件、精确引用替换、空缓存还原及构建、空库迁移和 Swagger 检查的完整命令。独立新装使用公开可定位的固定指南版本，以及消费者自行准备的 SDK、测试 SQL Server 和凭据。记录公开包解析和实际进程结果，Release 引用已实跑的指南版本。[发布者正式公开验收](../2026-11-26-prepare-r5-mapping-patch-release/release-handoff.md#正式公开后的验收)

## Risks / Trade-offs

- 包分批出现时，部分消费者可以先取得引擎。GitHub Release 须等三个主包、三个符号包、三个 PDB 和十个沿用包核验通过，并完成实际公开源 `install`、`upgrade` 和独立消费者新装。
- 若用户暂时切回 R4，按手册成组恢复适配器、Collection 和引擎版本。历史同库切换证据覆盖 R4 阶段创建的业务用户和随后的登录行，发行说明应标明其来源，并分别列出本轮 R5 实际公开源实测。[回退范围](../../../../docs/maintenance/r5-automapper-template.md#支持范围与公开发行交接)
