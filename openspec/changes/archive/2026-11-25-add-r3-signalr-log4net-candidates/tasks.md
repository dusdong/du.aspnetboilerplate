# R3 第二包实施任务

## 1. 框架子仓候选生产

- [x] 1.1 在两个组件增加显式 R3 候选模式。用普通与候选 MSBuild 求值核对原包 ID、`net9.0`、程序集及根命名空间、核心项目引用与精确包引用、共享框架和普通第三方声明。以固定 `457be917` 源码隔离构建同目标普通对照，在实现后的两个原项目关闭候选模式，构建并各执行一次 Release `pack`。回读普通包 `.nuspec`，逐项核对原包 ID、`net9.0` 组的原 `Abp` 依赖、SignalR 的 `Microsoft.AspNetCore.App` 框架引用和 Log4Net 的 `log4net` 依赖范围。运行现有 `Abp.Castle.Log4Net.Tests` 定向用例，分别保留结果和源码测试的覆盖范围。
- [x] 1.2 新增独立打包入口及从源码生产新候选的说明。锁定原 R2 核心归档及 `net9.0` DLL 摘要，隔离还原后用同配置打包。回读 nuspec、符号和 DLL，对照固定普通输出的程序集身份、API 和资源，核对许可、图标及实际编译资产。用同版本不同字节的核心包副本确认打包拒绝并定位归档。锁定一批实际交验输入，留存源码证明、生产日志与资产、清单、两份 `.nupkg` 和两份 `.snupkg` 及摘要。

## 2. 主仓实际包还原与构建

- [x] 2.1 添加独立消费者及 `r3-signalr-log4net` profile，使用 1.2 锁定的 R3 包、符号、清单及生产来源证据，并核对 R2 三个原包。按[设计](design.md)从独立空缓存和映射源还原，核对实际五包四边及第三方声明、解析、资产和哈希，随后使用同一资产做 Release 构建。实读 `.deps.json`、输出归属、目标和摘要。回归检查 R0、R2 和 R3 首包参数分派。
- [x] 2.2 用独立证据目录覆盖替换 R2 核心实物、改掉候选 nuspec 中的预期核心范围或原 ID 混入、缺失或错误目标及重复框架资产。用阶段夹具在还原前从受控源副本移走一个必需包并实际执行 NuGet 还原，核对非零及包 ID。每个负例检查诊断和未执行阶段。

## 3. 主仓定向运行和复跑说明

- [x] 3.1 接入真实回环 Kestrel、ABP/Castle、SignalR Hub 和本轮测试身份。连接后查询由 `OnlineClientHubBase.OnConnectedAsync` 登记的连接 ID 与身份，另行检查 `Register` 可调用。从宿主 `INotificationConfiguration.Notifiers` 查找 `SignalRRealTimeNotifier`，缺项即在发送前报告失败。按查得的类型沿用分发器的解析方式获取 `IRealTimeNotifier`，留存所选类型，并在客户端核对实际收到的 `getNotification` 负载。断开后按同一连接 ID 检查移除。留存客户端断言和加载身份，用缺失通知和未移除记录的证据副本核对诊断。
- [x] 3.2 按模板方式在同一宿主接入 Log4Net，记录唯一标识并读回文件中的等级、类别、完整消息。校验运行中五个框架程序集和 `log4net.dll` 的路径、身份及摘要。用只有文件或文本不符的证据副本核对失败。核对成功、失败和超时路径的宿主停止与报告留存。
- [x] 3.3 先编写验收文档和索引，分别列明从源码生产新候选、使用已有实物复验消费的命令。消费示例显式传入 `--dotnet`，注明首次验收所用的 R2 私有可执行文件路径、SDK 和两项共享运行时预期版本。回读原版 `10.2.0` 与 `log4net 3.1.0` 对照，核对报告能分别登记维护源码声明 `3.3.2` 对应的依赖范围、实选版本和资产。

## 4. 本机集成验收

- [x] 4.1 在 macOS ARM64 的新运行目录与空缓存中复验 1.2 锁定的同一批实物。核对清单、两份 `.nupkg`、两份 `.snupkg`、生产来源证据及确切 R2 原包，以设计中指定的 R2 `--dotnet` 路径完成还原、构建及宿主运行。核对所选 SDK `10.0.404`、进程架构 ARM64 和进程实际加载的 `Microsoft.NETCore.App`、`Microsoft.AspNetCore.App` 均为 `9.0.23`。回读生产与消费图、加载摘要、两条行为证据、停机和失败诊断。首次通过后登记最终报告路径与摘要、关联的生产证据、命令、退出码和未覆盖组合。若候选的生产源码、依赖或包字节需要变更，递增版本，重做受影响的生产与消费验收并记录换批原因。核对各仓差异、历史实物及 `git diff --check`，运行 `openspec-cn validate --all --strict --no-interactive`。

## Workflow follow-up

- 本机验收完成后，按授权分别处理 Git 交付与归档。若获 Git 交付授权，先核对框架候选来源树和待交付子仓提交的对应关系，确认该提交可从 `.gitmodules` 指定仓库取得，再交付主仓 gitlink，并以 `git ls-tree` 回读。归档按获准的工作流单独执行。
