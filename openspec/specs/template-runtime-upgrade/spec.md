# template-runtime-upgrade Specification

## Purpose

让使用经典模板和维护包的应用可以在已有 SQL Server 数据上升级运行时，并由维护者核对真实处理业务请求的程序集、迁移使用的数据库，以及同一用户升级前后的权限、查询结果和写入。

## Requirements

### Requirement: 完整模板按升级目标选择维护包资产

验证入口 SHALL 从固定维护包版模板的干净副本和空 NuGet 缓存构建 Web.Host、Migrator 及其可达项目，生成以 `net10.0` 为目标的 Release 产物，并可按入口追溯编译与运行资产。

#### Scenario: 冻结维护包在新目标下还原

- **WHEN** 维护者对正式 .NET 9 换包轮的模板和包清单重放运行时升级
- **THEN** 六个模板工程均以 `net10.0` 构建，Host 的包图包含已登记的 11 个维护框架包及两个映射包，Migrator 按自身可达图核验
- **AND** 对初始冻结组合，五个双目标核心包选用 `net10.0`，六个单目标框架包选用 `net9.0`，两个映射包选用 `net8.0`。各项可核对包 ID、版本、来源、归档摘要、包内资产及其摘要
- **AND** 两入口可核对 EF Core、Relational、SQL Server Provider 的 10.0 补丁版本及 SqlClient 的实际解析版本和运行资产

#### Scenario: 候选包或资产不相容

- **WHEN** 出现冻结输入摘要不符、旧发行线混入、有同名 DLL 来源冲突，或还原、构建、运行暴露候选不兼容
- **THEN** 报告标明出错入口、阶段、具体包和资产，当前组合验收失败。需换包时，另行登记候选版本及摘要，并以新组合重验受影响的结论

### Requirement: Migrator 在已运行维护版应用的同一数据库上升级

升级入口 SHALL 从已实际运行维护版 .NET 9 业务的 SQL Server 候选库接续，在同一数据库执行 .NET 10 Migrator，并保留升级前状态、既有迁移记录与业务数据的可核查对照。

#### Scenario: .NET 9 业务建立可恢复的升级起点

- **WHEN** 从指定登录前备份恢复专用候选库和独立对照库，并运行 .NET 9 维护包版的既有登录及查询
- **THEN** 同一账号的成功登录计数由候选库和对照库的 `1/1` 变为 `2/1`，记录两库身份、候选库新增登录记录的标识、30 条既有迁移及租户授权和查询结果，保存可验证的候选库升级前备份

#### Scenario: .NET 10 Migrator 接手已运行 .NET 9 业务的候选库

- **WHEN** .NET 9 应用退出，.NET 10 Release Migrator 执行迁移
- **THEN** 实际迁移连接指向 .NET 9 阶段的候选实例和数据库。该连接记录中的 PID 与执行迁移的进程一致，其入口 DLL 摘要匹配本轮 Release Migrator，其实际共享运行时及加载的 EF Core、SQL Server Provider 与本轮登记的 .NET 10 / EF Core 10 组合一致
- **AND** 原有 30 条迁移的 ID 与 `ProductVersion` 逐条一致，既有业务数据及登录记录完整，两库登录计数仍为 `2/1`。比较候选库模板业务表的列、键、索引和外键定义。无需新迁移时，迁移历史与业务表定义均与迁移前一致。确需新迁移时，先登记新增迁移 ID、预期结构差异和数据影响，从同一升级前恢复点复跑，实际增量须与登记逐项一致

#### Scenario: 表面成功但升级证据不成立

- **WHEN** 升级阶段误用 .NET 9 Migrator 连到正确候选库、Migrator 连到对照库、缺少连接或进程版本证据、候选库被重置、既有业务写入消失，或出现未说明的模型与结构差异
- **THEN** 升级验证在启动 .NET 10 Host 前失败，并记录预期值、观测值或缺失的证据，即便 Migrator 退出码为零

### Requirement: 目标 Host 使用已核对的运行资产提供原有业务

升级后的 Release Host SHALL 在指定的 .NET 10 和 ASP.NET Core 10 共享运行时上处理同一 Angular 客户端的租户登录与授权查询，并将响应、实际加载的维护包和 SQL 运行链关联至同一进程。

#### Scenario: 核对处理请求的进程

- **WHEN** 浏览器向本轮 Host 发起业务请求
- **THEN** 从该 Host 的启动及加载记录核对两项共享运行时、11 个既有身份的框架 DLL、唯一的维护版 AutoMapper 引擎及 EF Core 10 SQL Server 运行链，加载资产可追溯至本轮输出和来源
- **AND** 单独记录 AutoMapper.Collection 的还原、输出及实际加载情况。本轮路径未加载时，报告明确这一观测结果

#### Scenario: 升级后真实租户查询与写入延续

- **WHEN** 使用冻结 Angular production 客户端在新的浏览器会话中登录 `Default` 租户，使用同一授权账号提交相同关键词查询
- **THEN** 实际请求的用户具有 `Pages.Users` 权限，查询返回 HTTP 200、总数 1、唯一用户 ID 3，页面唯一用户名单元格与基线一致
- **AND** 候选库保留 .NET 9 阶段的成功登录记录，新增本次账号的成功登录记录，两库计数从 `2/1` 变为 `3/1`

#### Scenario: 页面正常但实际运行组合或数据有偏差

- **WHEN** 共享运行时主版本或登记的补丁版本不符、加载了错误的框架或 SQL Provider 资产，或查询成功但登录写到了其他库
- **THEN** 报告给出预期值与实际值，并将该次业务验收判为失败

### Requirement: 升级结果可供复跑与回退验证使用

维护者 SHALL 能从本轮记录重放同一升级路径，并定位升级前后数据库状态、对应应用及已观测的写入边界，供下一轮恢复原版应用时核验。

#### Scenario: 完成整轮验收并移交

- **WHEN** 干净构建、同库迁移、进程核对与真实业务全部通过
- **THEN** 留存模板和包输入、补丁、环境及命令。按备份集 ID 与文件 SHA-256 核对升级前、后两份备份，将其分别恢复到两个独立的新临时库。各库的迁移历史须与对应阶段一致（含迁移 ID 和 `ProductVersion`）
- **AND** 从两个恢复库回读 `Default` 租户账号 2 的成功登录行标识并与各阶段记录核对。升级前为 2 条，含 .NET 9 当轮登录行。升级后为 3 条，完整保留前两条，新增行与 .NET 10 当轮登录相符。交接记录列明恢复到升级前时会失去的登录行、实测组合及原版应用回退的待验状态

#### Scenario: 只完成了构建或局部运行

- **WHEN** 仅完成还原、构建或启动，缺少业务所用数据库、进程和请求之间的关联，或任一备份未成功恢复并读回对应阶段的数据
- **THEN** 报告停在已验证的阶段，记录缺项及首个可定位的错误，完整模板升级保持待验
