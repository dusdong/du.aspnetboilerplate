# maintenance-baseline Specification

## Purpose

为框架维护、独立包发行和存量应用迁移提供共同的对照基准。维护者能够追溯源码来源、核对候选包的依赖范围，并根据可重复的验证记录判断后续变更造成的差异。

## Requirements

### Requirement: 维护来源可追溯

主仓 SHALL 为维护基线和已识别的兼容参考记录对应的来源仓库、完整 Git 提交和用途。参考版本与当前子模块检出状态分别记录。

#### Scenario: 重建同一框架基线

- **WHEN** 维护者准备重现一次基线构建
- **THEN** 可以从记录定位到框架上游版本、对应的完整提交和用于比较的构建输入

#### Scenario: 参考版本和当前检出版本不同

- **WHEN** 某一子模块当前检出与为存量消费者选择的参考版本不同
- **THEN** 记录给出两者的用途、参考提交及验证状态，当前检出状态可由主仓 Git 子模块引用核对

### Requirement: 候选包身份和内部依赖可核对

主仓 SHALL 为首批候选包记录源码项目、原 `PackageId`、维护版 `PackageId`、程序集名、根命名空间、基线目标框架及内部依赖。

#### Scenario: 根包引入内部依赖

- **WHEN** 首批候选包直接或间接依赖其他框架包
- **THEN** 每个必要的内部依赖都有唯一的维护版包映射，清单中的依赖可递归解析至已有候选条目

#### Scenario: 选择维护版包标识

- **WHEN** 为框架现有项目增加 `Du.` NuGet 前缀
- **THEN** 候选映射记录原有程序集名和根命名空间，形成供后续发包验证的对照基准

### Requirement: 公共 API 可逐项比较

主仓 SHALL 为五个候选包对应的原版 Release 程序集保存机器可读清单，覆盖程序集身份、对外可见类型的完整名称、对外可见成员签名和清单资源名称，并记录从产物提取清单的命令。

#### Scenario: 识别同名程序集中的签名变化

- **WHEN** 对照清单中的某个公开方法仅改变参数类型，程序集身份保持一致
- **THEN** 比较结果能定位到对应程序集、类型及变化前后的签名，同一产物重复提取得到一致清单

### Requirement: 实际 NuGet 还原结果可复核

主仓 SHALL 按项目、目标框架及适用的运行时标识记录基线构建和回归实际解析的直接与传递 NuGet 包 ID 和版本，并保留脱敏的有效包源和可复现的还原命令。

#### Scenario: 传递依赖解析发生变化

- **WHEN** 在独立检出中执行记录的还原命令并比较两次结果
- **THEN** 能核对各目标使用的完整包版本集合，并定位新增、缺失或版本不同的包

### Requirement: 模板依赖缺口可核对

主仓 SHALL 将固定模板后端各项目声明的 ABP 包和版本与首批候选映射逐项核对，记录缺口及对应的消费验收范围。

#### Scenario: 模板使用首批范围以外的包

- **WHEN** 模板的 Core、Web.Core 或 Web.Host 项目声明了首批范围以外的映射、Module Zero、SignalR 或日志包
- **THEN** 基线列出引用项目、包 ID 和声明版本。首批候选包的验收对象为独立最小消费者，完整模板的验收条件为所选模板入口的框架依赖闭合

### Requirement: 基线结论由实际验证支撑

主仓 SHALL 将对照证据与精确框架提交、验证环境和覆盖范围关联，分别呈现通过、失败及未执行的项目。

#### Scenario: 复核原版核心行为

- **WHEN** 基线验证运行框架的核心、ASP.NET Core 和 EF Core 回归
- **THEN** 结果明确记录所用 SDK、操作系统、测试入口、数据库 Provider 和每个套件的实际结果，并能从该提交重现验证

#### Scenario: 某消费者或平台尚无实测证据

- **WHEN** 当前只掌握源码声明或其他平台的测试记录
- **THEN** 该消费组合保留为待验证，支持结论以实际测试组合为限
