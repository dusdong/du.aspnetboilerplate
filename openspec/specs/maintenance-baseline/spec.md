# maintenance-baseline Specification

## Purpose

为框架维护、独立包发行和存量应用迁移提供共同的对照基准。维护者能够追溯源码来源、核对候选包的依赖范围，并根据可重复的验证记录判断后续变更造成的差异。

## Requirements

### Requirement: 维护来源可追溯

主仓 SHALL 为维护基线和已识别的兼容参考记录对应的来源仓库、完整 Git 提交和用途。参考版本与当前子模块检出状态分别记录。

#### Scenario: 重建同一框架基线

- **WHEN** 维护者准备重现一次基线构建
- **THEN** 可以从记录定位到框架上游版本、对应的完整提交和用于比较的构建输入

#### Scenario: 参考版本和当前检出版本不同

- **WHEN** 某一子模块当前检出与为存量消费者选择的参考版本不同
- **THEN** 记录给出两者的用途、参考提交及验证状态，当前检出状态可由主仓 Git 子模块引用核对

### Requirement: 候选包身份和内部依赖可核对

主仓 SHALL 为首批候选包记录源码项目、原 `PackageId`、维护版 `PackageId`、程序集名、根命名空间、基线目标框架及内部依赖。

#### Scenario: 根包引入内部依赖

- **WHEN** 首批候选包直接或间接依赖其他框架包
- **THEN** 每个必要的内部依赖都有唯一的维护版包映射，清单中的依赖可递归解析至已有候选条目

#### Scenario: 选择维护版包标识

- **WHEN** 为框架现有项目增加 `Du.` NuGet 前缀
- **THEN** 候选映射记录原有程序集名和根命名空间，形成供后续发包验证的对照基准

### Requirement: 公共 API 可逐项比较

主仓 SHALL 为五个候选包对应的原版 Release 程序集保存机器可读清单，覆盖程序集身份、对外可见类型的完整名称、对外可见成员签名和清单资源名称，并记录从产物提取清单的命令。

#### Scenario: 识别同名程序集中的签名变化

- **WHEN** 对照清单中的某个公开方法仅改变参数类型，程序集身份保持一致
- **THEN** 比较结果能定位到对应程序集、类型及变化前后的签名，同一产物重复提取得到一致清单

### Requirement: 实际 NuGet 还原结果可复核

主仓 SHALL 按项目、目标框架及适用的运行时标识记录基线构建和回归实际解析的直接与传递 NuGet 包 ID 和版本，并保留脱敏的有效包源和可复现的还原命令。

#### Scenario: 传递依赖解析发生变化

- **WHEN** 在独立检出中执行记录的还原命令并比较两次结果
- **THEN** 能核对各目标使用的完整包版本集合，并定位新增、缺失或版本不同的包

### Requirement: 模板依赖缺口可核对

主仓 SHALL 将固定模板后端各项目声明的 ABP 包和版本与首批候选映射逐项核对，记录缺口及对应的消费验收范围。

#### Scenario: 模板使用首批范围以外的包

- **WHEN** 模板的 Core、Web.Core 或 Web.Host 项目声明了首批范围以外的映射、Module Zero、SignalR 或日志包
- **THEN** 基线列出引用项目、包 ID 和声明版本。首批候选包的验收对象为独立最小消费者，完整模板的验收条件为所选模板入口的框架依赖闭合

### Requirement: 基线结论由实际验证支撑

主仓 SHALL 将对照证据与精确框架提交、验证环境和覆盖范围关联，分别呈现通过、失败及未执行的项目。

#### Scenario: 复核原版核心行为

- **WHEN** 基线验证运行框架的核心、ASP.NET Core 和 EF Core 回归
- **THEN** 结果明确记录所用 SDK、操作系统、测试入口、数据库 Provider 和每个套件的实际结果，并能从该提交重现验证

#### Scenario: 某消费者或平台尚无实测证据

- **WHEN** 当前只掌握源码声明或其他平台的测试记录
- **THEN** 该消费组合保留为待验证，支持结论以实际测试组合为限

### Requirement: 统一入口复验固定 R0 源码

主仓 SHALL 提供一个读取已接受基线的 R0 复验命令，记录调用者的主仓输入、其框架 gitlink 和实际被验证的历史框架提交。该命令 SHALL 对固定 R0 源码执行独立还原、Release 构建、身份与 API 核对及三套真实回归。

#### Scenario: 在框架 gitlink 已推进的主仓上复验

- **WHEN** 当前主仓的 `aspnetboilerplate` gitlink 已推进到 R1，环境符合 R0 复验要求且固定 R0 提交可用
- **THEN** 命令在独立目录中使用 R0 提交，报告分别列出本次主仓输入、其框架 gitlink、历史 R0 主仓输入及实际参与构建的 R0 提交，且运行前后的当前框架检出相同、已接受基线内容一致

#### Scenario: 比较两次实际干净还原

- **WHEN** 主还原和第二次还原分别使用干净源码及互相独立的空 NuGet 包目录
- **THEN** 复验比较两次实际解析的 11 个项目和 11 个 `net9.0` 目标与已接受清单的项目引用、直接及传递包版本、包来源及内容哈希，报告将第二次还原的覆盖范围标为仅还原复验
- **AND** 三方比较一致后，复验使用同一 `primary` 目录及还原产物继续身份核对、Release 构建、API 比较和 .NET 回归

#### Scenario: 核对五个原版 Release 产物

- **WHEN** 主还原后的 Release 构建生成五个框架 DLL
- **THEN** 复验逐项核对五个项目的原 `PackageId`、`AssemblyName`、`RootNamespace` 和内部项目引用，以及实际 DLL 的程序集身份、对外可见类型全名、成员签名和清单资源名，并记录实际 DLL 的摘要
- **AND** 每个 DLL 两次提取的清单一致，独立构建的 DLL 摘要变化不影响程序集身份与 API 相同的判定

#### Scenario: 执行三套完整的真实回归

- **WHEN** 复验以主轮构建产物执行 `Abp.Tests`、`Abp.AspNetCore.Tests` 和 `Abp.EntityFrameworkCore.Tests`
- **THEN** 复验从当次三个 TRX 的 `UnitTestResult` 明细统计结果，按完整测试名精确匹配两项原有跳过，并与汇总 `total`、`executed`、`passed`、`failed` 和 `notExecuted` 交叉核对。成功报告合计 1313 通过、0 失败、2 原有跳过，并记录 EF Core 的实际 SQLite 环境
- **AND** 当核心套件明细为 1105 项通过、两项基线已有的具名 `NotExecuted`，且其余关键计数一致时，汇总 `notExecuted=0` 与明细的差异记录为已知现象，结果仍可通过

### Requirement: 基线复验失败可定位

R0 命令 SHALL 仅在所有必需步骤成功且实际证据与基线一致时返回零。命令 SHALL 保存机器可读报告，记录运行输入、环境、实际步骤和证据路径，区分通过、失败和未执行。

#### Scenario: 必需输入缺失或执行条件不受支持

- **WHEN** R0 固定提交或必要基线清单不可读取，或实际 SDK 与平台不符合该 profile 的执行要求
- **THEN** 命令返回非零，报告缺失或不符合条件的输入与未执行范围

#### Scenario: 产物或实际依赖偏离预期

- **WHEN** 实际还原图或项目身份存在差异、Release DLL 缺失，或同名类型的成员签名发生变化
- **THEN** 命令返回非零，报告受影响的项目、目标、程序集或类型，并保留已生成的证据及可取得的逐项差异
- **AND** 若差异出现在还原图，命令在三方比较处停止，构建、API 比较和 .NET 回归均未启动，并在报告中标为未执行

#### Scenario: 测试命令成功但没有可用的结果

- **WHEN** 任一测试命令返回零，但 TRX 或用例明细缺失、无法读取、零匹配、关键计数矛盾或出现基线以外的跳过项
- **THEN** 命令返回非零，并定位到套件、证据路径与差异或失败原因

### Requirement: 主仓 CI 执行同一 R0 复验

主仓 CI SHALL 先执行轻量 Python 定向验证，只有在实际执行有效用例且验证通过后，才在实际检出的主仓输入上运行与本地相同的完整 R0 命令。CI SHALL 传播失败状态，留存自检诊断及已取得的证据。真实 CI 验收 SHALL 关联实际执行记录与对应的主仓提交、固定框架输入和证据包。

#### Scenario: 统一命令在主仓 CI 通过

- **WHEN** 主仓工作流准备好所需环境和固定框架对象，Python 定向验证实际执行有效用例并通过，且同一 R0 命令的所有必需步骤通过
- **THEN** CI 记录实际 runner、主仓执行提交、R0 框架提交和自检结果，发布本次报告、依赖与 API 证据及三份 TRX

#### Scenario: CI 自检失败或未执行有效用例

- **WHEN** 前置 Python 定向验证失败或有效执行数为零
- **THEN** CI 将该次执行标为失败，保留自检日志和诊断，完整 R0 命令未启动且未生成其报告或 TRX

#### Scenario: 统一命令在主仓 CI 失败

- **WHEN** 主仓工作流中的 R0 命令退出非零
- **THEN** CI 将该次复验标记为失败，并尝试留存当次已经生成的报告、日志或部分证据
