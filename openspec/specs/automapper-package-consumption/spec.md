# automapper-package-consumption Specification

## Purpose

让经典 ABP 应用可以从可追溯的映射候选包启动既有配置，并在切换维护版本时用同一组业务输入核对用户更新、集合元素身份和关系型查询结果。维护者可以按冻结的包和补丁证据复核每次兼容结论。

## Requirements

### Requirement: 三份映射候选可追溯到兼容基线

维护者 SHALL 能从候选清单核对每个主包、符号包、实际生产源码、许可与安全维护结论。

#### Scenario: 核对同一批映射产物

- **WHEN** 维护者检查三份实际候选及对应符号包
- **THEN** 清单给出各仓库、固定参考提交、实际生产提交或可重放的源码树、补丁来源及归档摘要
- **AND** 与同目标原版相比，三个组件保留程序集名称、根命名空间和公开类型全名，报告核对程序集身份（含公钥标记）、公开 API 和目标框架

#### Scenario: 在干净 macOS 检出上执行引擎 API 比较

- **WHEN** 维护者在 macOS ARM64 干净检出上分别执行普通 Release 与候选引擎构建
- **THEN** 两次构建都实际运行 ApiCompat 并通过，报告记录复跑入口、历史参考包 ID 和版本、包内 DLL 路径、包与 DLL 的 SHA-256 及两次比较结果
- **AND** 输入缺失、摘要错误、跳过比较或比较失败时，验收返回非零并指出失败阶段

#### Scenario: 判断安全修复能否纳入候选

- **WHEN** 为兼容指南登记的三则公告判定候选是否通过
- **THEN** 每一项列出适用性、修复或不受影响的依据、涉及的源码及补丁来源与许可，关联冻结 `Du.AutoMapper` 主包和加载 DLL 的 SHA-256，并保存约定行为的触发条件、预期与实际结果
- **AND** 仅 GHSA-gpwp-5797-mjff 的 CLR 低栈分支同时以三项证据验收。核对冻结主包 DLL 中 `Mapper.MapCore` 调用 `RuntimeHelpers.EnsureSufficientExecutionStack` 的 IL，核对 .NET 9 官方文档的异常契约，并在加载同一冻结 DLL 的隔离子进程中用受控异常实测应用层的传播与恢复。探针须验证收到同一个注入的 `InsufficientExecutionStackException` 对象或含该对象的包装链，同一 Mapper 随后须完成正常映射并返回预期值。报告明确记录异常由测试注入，实际 CLR 低栈触发未观测
- **AND** 其余约定行为与异常均使用冻结主包 DLL 在隔离子进程动态复验。约定可恢复时，同一子进程中的同一个 Mapper 随后完成一次正常映射并返回预期值。证据缺失、处置未解决、断言失败、非预期退出或超时均判为失败

### Requirement: 适配器的独立包闭包只加载一套映射引擎

消费者 SHALL 能只直接引用维护版适配器，从指定包源还原映射栈及 ABP 内核，使用经典 ABP 的模块和依赖解析入口运行。

#### Scenario: 从空缓存安装并启动模块

- **WHEN** 独立消费者只直接引用三个映射包中的 `Du.Abp.AutoMapper` 且通过它传递取得 ABP 内核
- **THEN** 适配器主包 nuspec 对本批引擎、Collection 和冻结 `Du.Abp` 各声明一条 `[精确版本]` 依赖，Collection 主包 nuspec 对同一引擎声明一条 `[精确版本]` 依赖。四条声明逐一命中还原图，包图中无原版映射包或上游 ABP 包回流
- **AND** 从 Castle 解析的映射服务可用，静态兼容入口可用，三份映射 DLL 的包内资产、Release 输出和实际加载文件逐一同摘要
- **AND** Castle 解析、静态入口调用和按键集合映射完成后，枚举进程内全部 `AssemblyLoadContext`，简单名为 `AutoMapper` 的程序集实例恰好一个。报告记录加载上下文、程序集全名、路径及 SHA-256

#### Scenario: 冻结输入、依赖声明或加载实例异常

- **WHEN** 传递引擎缺包、冻结包摘要错误、内部边使用最低版本范围、同名 DLL 来自另一发行包，或相同字节的引擎在两个加载上下文各有一个实例
- **THEN** 验证返回非零并指出失败阶段及对应的包、依赖边或程序集。范围错误时列明预期与实际声明，重复加载时列出各实例的上下文和路径

### Requirement: 模板既有映射配置可更新同一用户实例

消费者 SHALL 能沿用固定模板的 Profile、属性映射和配置扫描入口，对已有用户执行与原版一致的更新。

#### Scenario: 保留模板中重复声明的映射

- **WHEN** 原版与候选分别加载相同模板配置，通过 `IObjectMapper` 将同一 DTO 映射到已有角色和创建时间的用户实例
- **THEN** 两次均能完成模块启动和映射，返回原目标实例，可更新字段取得 DTO 值
- **AND** 角色集合的引用及成员、创建时间保留原值，报告记录配置和输入来源、两侧运行结果及差异

### Requirement: 按键更新保留匹配元素身份

消费者 SHALL 能按既有键配置更新目标集合，并保留原版对匹配项、新项和移除项的处理语义。

#### Scenario: 通过经典 ABP 的键标记更新集合

- **WHEN** 原版与候选使用同一组独立的集合测试类型，启用 `AddCollectionMappers` 和 ABP 的 `AutoMapKey` 配置，对含保留项和待删除项的目标集合映射包含更新项和新项的输入
- **THEN** 两侧得到相同的键和值，匹配项保留原对象引用，新项出现一次，删除项消失，集合实例行为与原版一致
- **AND** 候选进程按程序集名加载的 Collection 来自本批主包

### Requirement: 查询投影在关系型数据库上执行

消费者 SHALL 能通过经典 ABP 的 `IObjectMapper.ProjectTo` 在关系型数据库执行查询，并取得与原版一致的投影结果。

#### Scenario: 比较同一查询的两次数据库结果

- **WHEN** 原版与候选在相同 SQLite Provider 版本及种子上筛选并排序模板 `User` 查询，通过 `IObjectMapper.ProjectTo<UserDto>` 投影后物化
- **THEN** 两侧的实际执行 SQL 均包含约定的筛选和排序，结果行、字段值及顺序命中已知预期，报告保留 Provider 版本、执行 SQL 和参数
- **AND** 从原版投影表达式和实际执行 SQL 确认取列及 `FullName` 的计算位置。候选取列或计算位置发生变化时，即使返回值一致也判为失败，并指出差异。SQL 别名和空白允许差异

### Requirement: 冻结批次可独立复验

维护者 SHALL 能按验收报告重跑同一批映射候选，并定位缺失的输入或未通过的业务断言。

#### Scenario: 复跑冻结候选

- **WHEN** 使用登记的原包、独立空缓存和相同输入重新运行消费验收
- **THEN** 报告给出实际运行环境、解析版本、包摘要和各项业务断言结果。任一必需断言未执行或失败时，入口返回非零并注明阶段

### Requirement: 内建集合映射的业务结果与顺序无关

引擎 SHALL 在业务类型、成员配置和输入等价时，按既有深度和引用规则映射普通集合。交换互不冲突的类型映射的注册或预热顺序，应得到相同且符合预期的业务结果。消费者可继续使用普通 `Map` 调用。

#### Scenario: 共享集合类型的两个业务成员先后映射

- **WHEN** 两个包含同种集合成员的类型映射共享普通元素映射，其中一个包含成员的映射配置了深度限制。消费者使用新建等价配置，固定注册顺序，只交换预热调用顺序，再对等价输入和目标状态执行同一映射
- **THEN** 候选均返回预期的成员值、元素数量、顺序及深度边界，普通调用无需额外映射选项

#### Scenario: 冷启动交换配置注册顺序

- **WHEN** 消费者使用新建等价配置，无预热，只交换同一组关联类型映射的注册顺序，再对等价输入和目标状态首次执行同一映射，随后重复调用
- **THEN** 候选两种顺序的首次和后续结果均符合相同的预期；包含成员或元素自身启用深度或引用保持时，约定的截断和引用身份仍成立

#### Scenario: 核对旧版运行确实加载公开包资产

- **WHEN** 独立消费者通过精确 `PackageReference` 引用 `Du.AutoMapper [14.0.0]`，在隔离空缓存从 nuget.org 还原并执行旧版对照
- **THEN** 实际还原图中的身份、资产及来源符合预期，实际还原 `.nupkg` 的 SHA-256 与 R4 已验公开下载摘要一致，进程实际加载路径上的 DLL 与该归档内 `lib/net8.0/AutoMapper.dll` 的 SHA-256 一致
- **AND** 源码引用或回退、其他包、来源或摘要不符时，该次运行缺少发行包行为证据，应修正输入并复测

#### Scenario: 正式冻结前验证顺序影响及候选结果

- **WHEN** 用已对账的公开旧包和实际候选主包，在隔离的普通 `Map` 路径上按预先确定的有界业务输入与预期独立运行上述成对顺序，并按原条件重复确认
- **THEN** 正式冻结及交接须有至少一对旧包结果或异常仅因注册或预热顺序变化而稳定不同，且至少一侧偏离预期。实际候选在同组条件下均符合预期。报告记录已复现的因素、用例条件、两侧结果或异常和实际加载 DLL 的路径及 SHA-256
- **AND** 若各顺序出现相同错误，报告保留已证实的业务偏差，顺序影响仍待证。若未观测到偏差，报告列出已试条件。顺序影响待证时回到维护评估，分析和探索性构建可继续

#### Scenario: 内联用例完成后的定向核对

- **WHEN** 已测订单与发票各自内联集合逻辑，维护者在旧包与候选上运行一个预定业务结果的有界普通消费者，优先对两个集合成员配置 `MapAtRuntime()`，从父对象的普通 `Map` 入口分别对照等价配置的顺序
- **THEN** 报告分别登记业务结果与计划观测，说明两个成员是否实际复用同一集合执行计划，并按上一场景的实包及业务条件判断冻结
- **AND** 若旧包两种顺序均出现同一业务错误且候选均正确，先登记偏差和消费者收益，复议范围并更新适用的验收条件后再决定冻结。若没有业务偏差，则记录该用例覆盖的路径，结束本轮定向核对，待新的业务输入或上游证据再复查。候选结果偏离预期时保留失败记录并复查引擎

### Requirement: 补丁组合保留精确依赖与发行身份

维护者 SHALL 为引擎、Collection、适配器的主包和符号包冻结新的批次，逐项登记包版本、生产来源与摘要。固定模板中其余维护包继续采用已验的 R4 公开版本。

#### Scenario: 三包冻结前验收实际引擎候选

- **WHEN** 在 macOS ARM64 干净检出上制备并验收实际引擎候选，三包批次尚未生成
- **THEN** 保留普通 Release 和候选构建对原版 `AutoMapper 13.0.0` 的 ApiCompat，并通过第二项 ApiCompat 比较，左侧为已验公开 `Du.AutoMapper 14.0.0` 主包的 `lib/net8.0/AutoMapper.dll`，右侧为实际候选主包的对应 DLL。记录各自结果、包及程序集身份、资产路径与 SHA-256
- **AND** 引擎验收从验收端独立登记的本轮引擎主包及包内 DLL SHA-256 读取预期值，核对还原归档、包内 DLL、Release 输出和进程实际加载，再按既有证据边界运行三则公告的回归
- **AND** 正式冻结时逐项对账已验引擎实物与摘要，有字节变化时重验受影响项后再冻结

#### Scenario: 只直接引用候选适配器

- **WHEN** 独立消费者从空缓存仅直接引用候选适配器
- **THEN** 发布物的 nuspec 和实际还原图均满足四条精确依赖：适配器引用候选引擎、候选 Collection 和 R4 内核，Collection 引用同一候选引擎。按键更新后进程只加载一份预期引擎，包内、编译、输出和实际加载的映射 DLL 能逐项对账

#### Scenario: 候选组合混入旧输入

- **WHEN** 保留旧适配器或旧 Collection 的引擎约束，或替换一个候选包却沿用原批次登记
- **THEN** 验收在依赖范围、来源或摘要检查时失败，并指出包和不一致项；强制覆盖传递版本所得的还原结果不能登记为通过

### Requirement: 固定模板的补丁结论绑定同批实包

模板验收 SHALL 将两代 Web.Host 和 Migrator 的实际包图、Release 资产、按需加载状态和业务观测绑定到同一份补丁组合。报告分别列出本轮实测及引用的历史证据。

#### Scenario: 新库安装及同库接续

- **WHEN** 用固定模板在独立新库上执行 `net10.0` 安装，并在独立迁移用例中由 `net9.0` 向 `net10.0` 接续同一 SQL Server 库
- **THEN** 新库迁移及 Host HTTP 检查通过，两代的 Host 和 Migrator 分别核对 13、10 个维护包。冻结客户端复验租户登录和授权用户查询，记录命中的数据库、预期用户及迁移前后数据变化

#### Scenario: 在固定运行时与同库上切换补丁并回退

- **WHEN** 固定模板在同一个隔离 SQL Server 库上按 `net10.0` 依次运行完整的公开 R4 组合、三个候选加十个 R4 包、完整的公开 R4 组合，并在首阶段写入可识别的业务记录
- **THEN** 候选和回退阶段均通过授权查询命中同一数据库、租户和业务记录，确认记录身份与数据。三阶段分别对账 Web.Host 和 Migrator 在各自入口范围内的包图、编译、Release 输出及按需实际加载，回退恢复公开 R4 的包版本及资产
- **AND** 记录旧版集合行为的局限、三阶段数据库状态与写入边界。若另行验证备份恢复，另记所选恢复点及其后的写入影响

#### Scenario: 切回公开旧版后仍可查询新版写入

- **WHEN** 固定模板在同一隔离 SQL Server 库、同一客户端和两套共享框架 `10.0.15` 上依次运行公开 R4、公开 R5、公开 R4，R4 和 R5 分别通过各自的应用在同一租户创建一个不同用户
- **THEN** 三阶段从独立空缓存仅用 nuget.org 还原，按各自发行的签后摘要核对 Web.Host 的 13 个、Migrator 的 10 个维护包及对应输出和实际加载资产。逐入口比较完整 `net10.0` 图的包 ID、解析版本、依赖边及约束和所选包资产，忽略缓存根路径差异。首末 R4 的图和包资产摘要一致，中段 R5 的差异限于已登记的三个映射包版本及对应 DLL 摘要、四条边的版本约束
- **AND** R5 查回 A，创建并查回 B。切回 R4 后，同一租户管理员在一个新登录的 Angular 会话中分别查询 A、B。报告为两次查询保留不同的请求标识及可独立回读的证据，各自关联创建回执、响应中的用户 ID 和业务字段、页面用户名、实际 Host 和查询连接
- **AND** 三阶段沿用同一数据库状态，报告核对 Migrator 的迁移连接、数据库身份、30 条迁移历史及各阶段的成功登录行。末段两次查询共用一次浏览器登录

#### Scenario: 包来源或业务读取无法对账

- **WHEN** 任一阶段的包源或签后摘要偏离发行记录，迁移或业务查询落在其他库，或授权查询无法唯一命中预期业务记录
- **THEN** 报告指出具体阶段、预期与实测值或缺失证据；包输入不符时在数据库操作前停止，业务阶段失败时记录已取得的写入证据和未执行步骤。只有三阶段均通过才登记该固定组合支持同库包回退

#### Scenario: R5 创建成功后授权查询失败

- **WHEN** R5 的 `User/Create` 已返回用户 B 的 ID，随后对 B 的授权查询失败
- **THEN** 失败报告仍可回读 R5 阶段、租户、用户名和创建返回的 ID，注明数据库读回结果或证据缺失，并分别标记该查询失败、末段 R4 未执行

### Requirement: 普通消费者可用公开材料验证映射补丁回退

消费者指南 SHALL 让固定模板的维护者只用指南、匿名可取得的源码和发行物，以及自己的工具、凭据和专用 SQL Server，完成 `net10.0` 上的 R4 → R5 → R4 同库演练。验收记录须标明所用指南的 SHA-256、实际运行的两个入口和逐阶段结果。

#### Scenario: 从干净目录切回自行保存的旧版

- **WHEN** 读者在干净目录分别从空缓存构建公开 R4 与 R5，保存 R4 的 Web.Host 与 Migrator。R4 在专用空库完成首次迁移并创建 A。R5 在同库查回 A、创建 B 并查回 B，然后停止 R5 Host
- **THEN** 两版的 Web.Host 各 13 个、Migrator 各 10 个维护包均与公开签后下载的版本、摘要一致。两个入口输出的三份映射 DLL 均可追溯到所选包成员。核对首段保存的 R4 输出后，直接从原目录依次运行 Migrator 和 Web.Host
- **AND** 三阶段的实例与数据库身份相同。以 R4 首次迁移后的 30 个迁移 ID 为基线，后两阶段各自的迁移前后均与基线逐项一致
- **AND** 末段取得同一租户管理员的一次新认证，两次授权查询分别唯一命中 A、B。各自响应的 ID、用户名对应本人的创建回执，业务字段对应创建时提交的值。租户身份由认证会话和对应用户的数据库行核实

#### Scenario: 启动前发现回退输入不符

- **WHEN** 包源或签后摘要不符、保存的 R4 输出与清单不符，或两入口的实际连接偏离隔离库
- **THEN** 在受影响阶段启动 Migrator 和写入业务前停止，指出入口或文件及预期与实际值。独立验收用 R4 运行目录的副本替换一个映射 DLL，保留校验失败、迁移未启动和业务未写入的结果

#### Scenario: 创建成功后授权查询失败

- **WHEN** R5 创建 B 已返回 ID，随后对 B 的查询失败、返回多条或查到了其他用户
- **THEN** 保留 B 的创建回执、此前 A 的读回结果，以及 B 的查询和数据库读回结果或缺项。登记 R5 失败、末段 R4 未执行，本轮独立演练未通过

#### Scenario: 回退后只查回一名用户

- **WHEN** 已切回保存的 R4，查询 A 成功，查询 B 未唯一命中与 B 创建回执相符的记录
- **THEN** 分别记录两次查询结果，保留两份创建回执和可取得的数据库读数，登记末段 R4 失败

#### Scenario: 指南步骤需要现场补充

- **WHEN** 读者必须使用发布者私有输入或指南以外的命令，才能完成任一阶段
- **THEN** 记录缺项，补齐公开步骤。修订后的指南以新摘要从干净目录和新的专用空库复验，成功路径与启动前停止检查均通过后才能登记独立消费者验收通过

### Requirement: 消费者可在同一 .NET 10 环境对照两代公开映射包

消费者 SHALL 能只用公开输入，用固定模板的 DTO、实体和 Profile，分别在 R4 与 R5 独立消费者中运行映射用例，核对实际加载的发行包，并将每个业务结果与预先登记的期望比较。

#### Scenario: 从两次独立还原确认公开发行身份

- **WHEN** 消费者使用同一份业务代码、SDK、运行时和 SQLite Provider，在各自的空缓存从 nuget.org 还原，只在三个映射包中直接引用该版适配器
- **THEN** 两侧分别解析到对应发行组合，三包的精确依赖边命中，实际消费的维护主包可逐个核对公开签后摘要，两张业务包图的包版本差异仅有三个映射包
- **AND** 各自记录三份映射程序集的所选包内资产、输出和加载文件摘要，调用结束时枚举全部加载上下文，每侧进程只加载一个引擎实例

#### Scenario: 独立消费者更新已有用户与按键集合

- **WHEN** 两版各自通过经典 ABP 的模块配置和 `IObjectMapper`，将 `IsActive = true` 的 `UserDto` 映射到 `IsActive = false` 的已有 `User`，并执行相同的按键集合映射
- **THEN** 各自返回原用户，其 `IsActive` 变为 `true`，其他普通字段命中输入，原角色集合、角色对象和创建时间保留
- **AND** 各自保留目标集合和键 10 的原对象并更新其值，删除键 20，创建一个键 30，最终有序键值为 `10:updated`、`30:inserted`

#### Scenario: 将同一查询实际发送给 SQLite 并物化

- **WHEN** 两侧以相同种子启动各自的 SQLite 数据库，对租户 6 的活跃用户执行 `ProjectTo<UserDto>` 并物化
- **THEN** 两侧各自捕获执行 SQL 和参数，核对租户、活跃条件、排序、读取列及其顺序，物化 ID 依次为 12、13、11，各 DTO 字段符合种子预期
- **AND** 投影表达式与真实取列证实 `FullName` 由客户端访问实体属性计算。SQL 别名和空白差异允许通过

#### Scenario: 输入或业务未达到约定

- **WHEN** 一侧包身份、运行环境或依赖图不符合对照条件，或一项业务断言失败、缺失或跳过
- **THEN** 验收入口返回非零，报告注明版本、阶段、预期和实测；输入校验失败时该侧不计入业务结果，已有原始输出可供定位与复测

#### Scenario: 第一侧物化后投影断言失败，第二侧独立完成

- **WHEN** 在定向反例中只交换第一侧预期列中的两列，两侧真实探针分别执行相同的 SQLite 查询并物化
- **THEN** 第一侧报告保留已通过的用户更新和按键集合结果，标记投影失败，列出预期和实际列顺序，并可回读实际 SQL、参数、投影表达式和物化行
- **AND** 第二侧独立完成全部三项并留下通过记录。总报告分别列出两侧状态和退出码，总入口返回非零
