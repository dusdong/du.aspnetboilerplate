# maintenance-release-review Specification

## Purpose

使维护者能够针对一个已经公开的版本，核对其源码、消费者实际解析的依赖和已知上游修复，说明哪些事项需要处理，并让下一轮维护者能复查结论、补齐证据和接续未决事项。

## Requirements

### Requirement: 审查可定位到确切的发行与消费者

维护记录 SHALL 关联公开 tag、其解引用提交、生产 gitlink、包 ID 与版本、固定消费者和实际还原图。记录注明审查时间和查询来源，逐仓分别登记上游比较基点、实际查询的分支或发行及截至查询时的完整 SHA。

#### Scenario: 首次审查已发行的维护包

- **WHEN** 维护者审查 `v10.5.1`
- **THEN** 可从记录复核 tag 指向的源码、三个生产仓及 13 个包，区分发行提交和收尾提交，并按 TFM 和入口复查两代 Web.Host 与 Migrator 的完整直接及传递包闭包
- **AND** 维护记录附精简清单，并登记每份原始 `project.assets.json` 的位置、SHA-256 和提取方式，按实际进程分别记录 .NET 和 ASP.NET Core 版本

#### Scenario: 一个依赖在不同入口或目标下解析不同

- **WHEN** 依赖只在特定入口出现或在两个 TFM 上解析出不同版本
- **THEN** 精简清单保留各入口和 TFM 的解析版本及引入路径，区分应用依赖、构建工具和进程共享运行时。复跑结果按原图和新图分别登记，差异可追溯到对应输入

### Requirement: 上游修复及公告须按实际适用性判定

维护记录 SHALL 为相关上游 PR、修复提交或公告列出原始来源、受影响的范围、发行源码或实包证据以及处理结论。首轮查询覆盖与已发行版本匹配的存量公告，以及较新维护线上适用于旧基点的修复。

#### Scenario: 公告使用上游包名或修复已经回补

- **WHEN** 公告针对原包名，或 fork 以不同提交引入等效修复
- **THEN** 通过原包与维护包映射逐项核对版本范围、维护源码和已有实包验收。相应结论关联 R4 实包的同一 DLL 或发行源码证据，并注明证据覆盖边界

#### Scenario: 只有传递依赖命中公告

- **WHEN** 消费者实际解析的第三方传递依赖落入公告版本范围
- **THEN** 记录从入口到该依赖的路径、命中版本和适用条件，分别说明维护包、模板、运行环境和消费者的处理责任与行动

#### Scenario: 来源不可用或覆盖不完整

- **WHEN** 上游查询失败、分页未完成、依赖图缺失或适用性证据不足
- **THEN** 记录具体缺项、受影响范围、重查条件和入口，单独标明待核实项。只有完成的覆盖范围可计入无相关发现

### Requirement: 首轮有可交接的补丁决定

维护者 SHALL 逐项登记需处理、已有修复、不适用、暂缓或待核实及证据，暂缓时说明理由及触发条件。再根据维护包证据给出需补丁、无需补丁或暂不能判定的整轮决定，分别列出模板、运行环境和消费者行动，保留复核入口与下轮起点。支持矩阵扩展必须引用该组合的实际验收结果。

#### Scenario: 存在需要修复的事项

- **WHEN** 已有证据确认维护包需要修复，其他事项可能仍待核实
- **THEN** 整轮决定为需补丁。列出优先项、消费者影响、负责仓库、拟修复范围、兼容或回退边界、定向回归及实包验收入口。已明确的修复可先单独立项，其他待核实项继续记录
- **AND** 补丁发行准备由验收端独立登记清单 SHA-256，供公开回读和消费核对使用同一可信摘要，并保留 R4 固定批次复验。若补丁变更选择主仓 OIDC，按手册交接待演练的只读验证（含替换包反例）和另获授权的凭据兑换及真实上传验收

#### Scenario: 本轮没有需要发行的补丁

- **WHEN** 核查证据支持继续使用现有维护包，包括行动仅涉及模板、运行环境或消费者的情形
- **THEN** 整轮决定为无需补丁，另列相应行动，记录依据、检查截止点与重新审查的触发条件。未实测的平台继续标为待验

#### Scenario: 现有证据影响整轮补丁决定

- **WHEN** 尚未确认维护包需要修复，且适用性或消费证据的缺失导致无法判断是否需要补丁
- **THEN** 将本轮决定记录为暂不能判定，列出影响的版本、入口或环境，以及补查条件和入口

### Requirement: 后续审查可从上一轮查询截止点接续

维护记录 SHALL 标出本轮审查的起止点、所用发行和实际消费图，并分别给出上游修复、依赖公告、共享运行时服务公告的新增、修订、撤回或无变化结论。独立补丁的冻结状态不影响运行环境和消费者事项的处置。

#### Scenario: 沿用同一公开发行进行下一轮审查

- **WHEN** 维护者接续上一轮已核对的发行和模板组合
- **THEN** 读者能从首轮分支表逐行找到三个上游仓库六条分支的起止完整 SHA、相关发行标签和变动结论，并能从公告查询截止点和四份还原图复查本轮覆盖及处理决定
- **AND** 包图或包身份变化时，按新图重新匹配直接、传递依赖和维护包的原身份。来源不可读或分页不完整时，记录缺项和补查条件，并保留该来源最后一次完整查询的位置

### Requirement: 存量应用可按已验组合判断迁移准备情况

运行时退出支持后，维护者 SHALL 给出以公开包为输入的迁移指引，标明运行时支持状态、适用组合、迁移前后的同库业务检查和恢复点的写入边界，区分历史实测、本轮实测及待验证的组合。

#### Scenario: 存量维护包用户从自己的源码构建并验证升级

- **WHEN** 应用已经使用公开 R4 维护包，维护者具备应用源码、公开包源、对应 SDK 和共享运行时、客户端及可恢复到隔离库的业务备份
- **THEN** 维护者可按指引定位要调整的工程、TFM 和直接包引用，从公开源还原并生成两代 Web.Host 和 Migrator 的 Release 输出。消费者步骤所需的文件均可从自己的应用、备份或公开来源取得
- **AND** 维护者可在隔离库建立源版本业务基线和升级前恢复点，用目标版本的两入口接续同一库，复核迁移历史及同一租户授权查询返回的同一条记录

#### Scenario: 固定消费者与已验迁移输入相符

- **WHEN** 维护者核对公开包及摘要、模板提交、两代实际加载的共享运行时、平台、数据库与客户端，均与既有验收输入一致
- **THEN** 指引可引用对应原始迁移报告及其摘要，标注历史实测日期。读者能复查两代 Web.Host 与 Migrator 的进程、目标库、迁移历史和同一租户在升级前后的授权查询结果，以及备份恢复会舍弃哪些后续写入

#### Scenario: 目标服务版本或消费者组合变化

- **WHEN** 拟用的目标补丁、依赖图或部署组合与已验输入有差异
- **THEN** 指引列出差异，注明相应组合待验。要登记迁移通过，须在隔离测试库实跑受影响的迁移与业务路径，核对两代两入口实际加载的 .NET 和 ASP.NET Core 版本，以及同库迁移和同一租户授权查询命中的业务记录
- **AND** 若仅更换目标共享运行时补丁，须确认两代各入口的 NuGet 包图分别与 R4 对应图一致。两套共享框架按该阶段预期版本核对启动选择和实际加载，EF Core 与 SQL Server Provider 的加载资产按该入口包图独立核对
- **AND** 来源覆盖不全、进程版本不符或库、租户、记录无法对账时，报告标明首个缺项或不一致。实测支持范围仅引用证据完整的组合

### Requirement: 跨公开补丁的审查能说明既有结论的适用范围

维护记录 SHALL 将新公开版本的实际消费图与上一版逐入口比较，说明哪些发行包、上游源码及运行时证据发生变化，以及先前的公告结论在新组合中是否仍然成立。

#### Scenario: 三个包更新且十个包沿用上次发行

- **WHEN** 消费者从上一公开版迁往只更新部分包的版本
- **THEN** 读者能按 TFM、入口查到更新和沿用的精确版本、签后摘要和引入路径，以及新增、移除或改变的依赖。沿用包可追溯到上一版的同一签后实物
- **AND** 公告匹配涵盖各入口全部实际包 ID 和解析版本。维护包另按上游原包 ID 收集公告，并用上游源码基点对应的版本判定区间。即使 fork 发行版本已在区间外，基点命中的公告仍须列出两组 ID 和版本，并以本版源码及实包证据说明处置

#### Scenario: 上游分支无新增提交但上轮仍有未决事项

- **WHEN** 上次截止前已有暂缓或待核实的上游事项，本轮分支终点未变
- **THEN** 维护记录逐项列出原复查条件、本轮是否满足及其依据，说明维持或更新后的处置是否影响整轮补丁决定。仍未决的事项保留下次复查条件

#### Scenario: 两次发行的入口包数相同

- **WHEN** 同一入口在两个发行版解析出相同数量的包，但有包版本、依赖关系或资产变化
- **THEN** 审查记录列出具体差异，并区分能以相同实物复用的核验与需要用新实物复查的判断。消费者能查到自己的入口受哪项变化影响

#### Scenario: 先前的公告仍缺组件范围

- **WHEN** 原始公告的组件或版本范围仍不可读，或缺少把入口实际资产与该范围关联的证据
- **THEN** 该项保留为待核实，记录受影响的判断、最后完整覆盖位置、补查入口和条件。维护包的整体决定说明此缺项是否影响判断，并分别列出消费者与运行环境的行动
