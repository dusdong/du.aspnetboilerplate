# template-maintenance-package-consumption Specification

## Purpose

让维护者从固定的真实模板安装已登记的维护包，在相同运行时、前端及数据库恢复点上比较原版和换包后的结果，并能从业务请求追溯到实际使用的框架程序集与数据库。

## Requirements

### Requirement: 完整模板从冻结实包干净还原

验证入口 SHALL 在固定模板的隔离副本重放换包步骤，以原有项目引用关系从独立空 NuGet 缓存还原 Web.Host 与 Migrator，并完成 `net9.0` Release 构建。

#### Scenario: 两个入口按各自项目图还原

- **WHEN** 安装已登记的 R2 核心、R3 集成组件、Module Zero、映射适配器及其两份映射依赖
- **THEN** Host 还原图中的维护包集合恰为指定的 11 个框架包和两个映射包，各项目的声明、解析版本、传递边、来源、包摘要和选中资产可逐项核对，Migrator 的集合按其自身入口核对
- **AND** 两个入口都没有引入旧框架包或原版映射包，报告记录相对原版的项目变更、第三方差异和 SQL Server Provider 实际组合

#### Scenario: 冻结输入或还原结果偏离

- **WHEN** 缺少登记实物、同版本包摘要不符、部分项目仍引用原包，或某个内部依赖被未登记来源满足
- **THEN** 入口返回非零，注明包、项目和失败阶段，在包组合通过前不启动数据库验收

### Requirement: 运行请求可追溯到唯一维护版程序集

维护版 Host SHALL 使用本次 Release 输出处理请求，保留现有程序集名与公共类型身份，并能从进程实际加载文件追溯至对应冻结归档。

#### Scenario: 将还原、输出和进程加载相互对照

- **WHEN** 维护版 Host 在 `Development` 环境中完成模板业务路径
- **THEN** 11 个预期框架程序集均有同一 Host 进程的加载证据，记录各自全名、加载上下文、路径与文件摘要，逐项匹配输出及候选包资产
- **AND** 报告核对两份映射包的输出来源，记录映射引擎、实际加载的映射扩展、SQL Server Provider 和 EF Core 的运行身份。同一 Host 实际加载的 `Microsoft.NETCore.App` 和 `Microsoft.AspNetCore.App` 均须为原版返修轮的 `9.0.10`，报告保留两者的加载路径和版本

#### Scenario: Host 选择了其他共享运行时补丁

- **WHEN** 正式对照中任一共享运行时的实际补丁版本偏离 `9.0.10`
- **THEN** 正式对照返回非零，记录两项运行时的期望值和实测值。其他补丁组合的结果单列。如需在该组合上判断换包影响，须用原版 Host 和候选 Host 在相同补丁组合、冻结前端和相同数据起点分别完成同一业务场景

#### Scenario: 已构建正确包却运行了其他副本

- **WHEN** 输出或进程中出现来源冲突、重复引擎实例，或必需的加载证据缺失，即使浏览器搜索返回预期用户
- **THEN** 运行验收失败，并能定位具体进程与程序集

### Requirement: 原版恢复点可供维护版 Migrator 与 Host 使用

维护者 SHALL 能按冻结身份恢复最终返修轮备份到本轮新库，运行维护版 Migrator，维持该模板的既有迁移历史与业务数据。

#### Scenario: 移交登录前状态

- **WHEN** 核对备份摘要和备份集 ID 后恢复到新的物理文件并运行维护版 `Migrator -q`
- **THEN** 从本轮 Migrator 实际执行迁移的 SQL 连接取得服务端实例名和 `DB_NAME()`，两项均匹配本轮登记的实例和候选库，记录可追溯到该 Migrator 进程
- **AND** 迁移器正常退出，运行前后 30 条迁移记录及版本、指定租户、管理员、授权和合成用户均与返修轮一致，登录前成功计数符合恢复点
- **AND** SQL 证据给出实际实例、库名、备份集、文件及恢复状态，保留的原版备份摘要与登记一致

#### Scenario: Migrator 错连对照库或缺少连接证据

- **WHEN** Migrator 的迁移连接指向从同一备份恢复的对照库、实际实例与登记不符，或缺少该连接的目标证据
- **THEN** 即使 Migrator 退出码为 0 且候选库仍有预期的 30 条迁移，验证入口也在启动 Host 前返回非零。报告指出预期目标、实际观测值或缺失项

#### Scenario: 恢复来源或目标不匹配

- **WHEN** 输入命中早期批次、恢复目标已存在、文件路径有冲突，或还原数据与原版预期不一致
- **THEN** 入口在对应阶段返回非零，避免覆盖已有库或文件，不再执行依赖该结果的登录验收

### Requirement: 同一前端及用户数据在换包后得到相同业务结果

维护版 Host SHALL 使用冻结 Angular 客户端完成真实租户登录与授权查询，使服务端会话、数据库、响应以及页面行都能与原版比较。

#### Scenario: 复跑最终返修轮的业务请求

- **WHEN** 全新浏览器上下文经模板页面选择 `Default` 租户，以既有账号登录后搜索 `r3usercf4314cdfe038c35`
- **THEN** 会话返回租户 ID 1 和登录用户 ID 2，具备 `Pages.Users`，实际 `User/GetAll` 请求携带该 `Keyword`，返回 HTTP 200、总数 1 与唯一用户 ID 3，唯一表格数据行的用户名与该关键词完全相等
- **AND** 浏览器提交登录前，租户 ID 1、账号 ID 2 的成功登录记录在两库各为 1。完成搜索后，候选库为 2，对照库为 1。报告关联同一前端构建、Host 进程、业务请求和两库的前后读数

#### Scenario: 提交登录前计数已偏离恢复点

- **WHEN** 浏览器即将提交登录时，任一库中该租户及账号的成功登录记录数不等于 1
- **THEN** 入口记录两库实测值，停止提交登录并返回非零

#### Scenario: 搜索通过但数据写入错误

- **WHEN** 实际登录增量落入对照库，或目标库增量不符
- **THEN** 即使会话、响应及页面与原版相同，入口仍返回非零，报告保留两库的前后计数与差异

### Requirement: 两代公开包可通过固定 Angular 模板对照用户角色编辑

验收 SHALL 在同一冻结 Angular production 构建下，使用公开 R4 和 R5 各自的固定模板后端完成真实用户编辑。每侧独立验证实际请求、服务端回执、重新打开后的界面和数据库已提交状态。角色验收以直接分配给目标用户的完整集合为准。

#### Scenario: 两侧从可比的独立环境打开同一业务初态

- **WHEN** 两侧分别启动已核验的公开包输出、专用 SQL Server 新库和独立浏览器会话，以授权管理员登录 `Default` 租户并打开该侧普通用户的编辑窗口
- **THEN** 页面实际加载同一已核验 production 构建，响应对应已登记的 Host、租户及用户。窗口的 GET 返回只有 A 的角色数组，GetRoles 提供 A、B 和其他可分配角色，页面仅勾选 A，同库独立 SQL 确认该用户仅有 A 的直接关联并记录普通字段和创建时间原值
- **AND** 首次编辑前，每侧均取得该浏览器会话实际收到的用户编辑脚本 `chunk-PPIUHYWS.js`，响应体的 SHA-256 与冻结清单中的同名条目一致
- **AND** 两侧种子的业务身份和初态等价，A、B 均为无业务授权的非管理角色

#### Scenario: 保持 A 的勾选并保存姓名

- **WHEN** 管理员在初始窗口修改姓名，保持角色勾选原样，通过页面保存
- **THEN** 实际 `PUT User/Update` 的 `roleNames` 为 `["DU-ROLE-A"]`，该用户的直接角色仍只有 A

#### Scenario: 改选 B 并保存姓名

- **WHEN** 保留 A 的阶段通过，管理员在同一用户的窗口取消 A、勾选 B 并再次修改姓名，通过页面保存
- **THEN** 实际 `PUT User/Update` 的 `roleNames` 为 `["DU-ROLE-B"]`，该用户的直接角色只有 B

#### Scenario: 取消全部并保存姓名

- **WHEN** 改选 B 的阶段通过，管理员在同一用户的窗口取消 B，确认全部角色均未勾选，再次修改姓名并通过页面保存
- **THEN** 实际 `PUT User/Update` 的 `roleNames` 为 `[]`，该用户的直接关联为零，A 和 B 角色定义仍存在

#### Scenario: 每次保存均可核对页面和持久结果

- **WHEN** 页面提交任一步角色编辑
- **THEN** 实际 PUT 的完整角色数组和姓名符合该步输入，且返回该目标用户的成功回执。本次保存触发新的 `GET User/GetAll`，查询携带 `Keyword=durolecheck`，成功响应的 `totalCount` 为 1，`items` 仅含本侧目标用户 ID 对应的记录，`fullName` 等于本步姓名加空格和种子姓氏 `User`
- **AND** 窗口关闭且列表唯一数据行显示 `durolecheck` 和本步新全名后，从该行重新打开编辑窗口。重新打开触发独立的 GET 和 GetRoles。GET 与回执的字段及角色集合符合该步预期，GetRoles 返回的角色逐项对应页面选项，全体实际勾选与 GET 的角色集合一致
- **AND** 浏览器请求、实际 Host、授权会话、目标租户及用户和数据库身份可关联。使用独立连接从该侧同库只读核对全部直接角色关联和用户字段。姓名取该步输入，其余可编辑字段及 SQL 创建时间保留各侧原值

#### Scenario: 运行中的数据库身份优先于业务结果

- **WHEN** 任一已发出的 PUT 或用户详情 GET 缺少可关联到该请求及目标用户的业务库身份，或该连接、独立 SQL 读回的实测库身份与本侧登记不符
- **THEN** 即使登录握手已通过、字段符合预期或同时缺少 PUT 回执，也判该侧输入不可比。记录失配或缺失的身份，停止该侧写入，已发出的 PUT 不重发
- **AND** 若观测提示该 PUT 可能写入另一侧库，另一侧在下次编辑写入前须用独立只读 SQL 核实库身份、目标用户字段、原创建时间和全部直接角色仍符合其当前步骤的预期起点。符合才继续，否则该侧输入不可比，后续依赖步骤标记未执行

#### Scenario: 单侧证据不完整或结果偏离

- **WHEN** 冻结输入、浏览器实收脚本或会话身份无法核实，或在身份可信时实际载荷、成功回执、列表刷新、重开状态或同库业务数据缺失或偏离预期
- **THEN** 输入或身份无法核实的侧判为不可比。身份可信而业务证据缺失或偏离的侧判为阶段失败。仅缺 PUT 回执时，即使只读诊断查得预期数据，该步仍失败。报告记录步骤、预期、实测与可用证据，停止该侧写入，不重发 PUT，后续依赖步骤标记未执行。满足当前步骤起点的另一侧独立验收
- **AND** 只有两侧各自完成符合预期的全部三步且输入可比时，总对照通过。两侧出现相同偏差时分别记录失败，共同前提无法核实时记录两侧不可比
